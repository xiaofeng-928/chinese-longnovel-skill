# 状态与总结

## 权威模型

状态和总结不是正文旁路事实，而是 current commit head 的可重建投影：

```text
committed 正文资产
  -> transaction 内不可变 summary/state delta
  -> current head CAS
  -> 总结/章节总结_第X-Y章.md
  -> 总结/主角状态仓库.md 与 总结/系统状态仓库.md
```

未审查 attempt 不生成正式总结，不更新仓库。双审查通过后只在 attempt 内暂存增量；状态回证通过、事务资产冻结并完成 head CAS 后，才物化共享总结和仓库。CAS 失败时暂存内容保持不可达，不能进入后续上下文。

主角状态仓库是当前真实状态权威源；章节总结只维护状态增量，不复制完整仓库；总大纲只维护计划状态。仓库与正文证据冲突时，以 current 链 committed 正文为准重建投影。

## 章节增量

每个 state delta 必须包含：

- `delta_id`、字段名、旧值、新值。
- `source_anchor` 与 `source_excerpt_sha256`，锚点必须真实存在于最终正文。
- `fact_lock_ids`，只能引用该 attempt 的事实锁。

`reviews/state.md` 绑定 `node_id`、`attempt_id`、最终正文哈希、状态增量文件哈希、提示词版本、时间和 `total_result: pass`。`scripts/validate_chapter_candidate.py --require-state-validation` 未通过时不能 prepare transaction。

## 章节总结模板

```markdown
<!-- MYNOVEL:SUMMARY:chapter-0001:START -->
- node_id: chapter-0001
- transaction_id: tx-...
- body_sha256: <64位>
- 关键事件：
- 角色状态增量：
- 硬事实与正文锚点：
- 角色认知增量：
- 能力/资源增量：
- 系统与经营增量：
- 信息流与关系增量：
- 因果债、伏笔与后文禁止误写：
- 章末状态：
<!-- MYNOVEL:SUMMARY:chapter-0001:END -->
```

重审或 rebase 只替换相同 node ID 的 current 投影块；历史 transaction 内增量不可改写。

## 主角状态仓库

仓库只保留最新状态，至少覆盖：身份与位置、能力成长、资源资产、身体装备、关系承诺、信息认知、目标债务、名声反馈和后文禁止误写。每个非空状态都保留最近变动 node ID 或正文证据。

资源必须分账：现实可搬运物资放入“资源与资产”；生存点、权限、图纸、模块和系统额度放入系统动态状态。实体物资转为系统资源必须有系统设计与正文证据。

## 系统仓库拆分

默认系统摘要可留在主角仓库。以下条件命中任意两项时，完整运行态拆到 `总结/系统状态仓库.md`：多种系统货币、系统商店、主角经营商店、三条以上成长路线、并行任务池、复杂库存/订单/利润或跨章冷却。

拆分后系统仓库保存权限、余额、商品/模块、任务、双商店、资源转换、限制与证据；主角仓库只保留摘要链接。禁止双重权威。

## 长期摘要预算

- 每 50 章生成一份阶段总结：阶段结算、关键时间锚、状态核对、角色进退、伏笔和未偿因果债。
- 每 200 章生成一份长期摘要，压缩前四份阶段总结；只保留仍影响后文的事实，并为已失效信息记录结束 node ID。
- 正文组装读取当前 50 章阶段总结和必要的 200 章长期摘要，不把全部历史总结无限拼入上下文。

## 提交流程

1. 自然化候选通过候选验证。
2. `reviews/naturalization.md` 与 `reviews/context.md` 两个不同 reviewer 独立通过，均绑定同一 `reviewed_sha256`。
3. 生成最终正文、summary delta、state delta；执行状态回证。
4. `prepare_transaction` 冻结正文、增量、三份审查证据和章节序列事件，记录 `state_validation_report_sha256`。
5. 项目写锁下复核 base head，CAS 推进 commit head。
6. 从新 head 物化章节序列、章节总结和状态仓库，更新 `materialized_head_transaction_id` 与 `materialized_head_sha256`。
7. 运行 `validate_project.py`；失败则项目保持可恢复状态，不声称提交成功。

用户只要求“写第X章”时停在候选态：不生成正式章节总结，不更新主角状态仓库/系统状态仓库，不推进章节序列或 commit head。
