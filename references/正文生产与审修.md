# 正文生产与审修

本文是正文生产、手动自然化、正式审查与修复的唯一流程文档。普通创作不自动自然化；创作提交、用户手动自然化与后置审查是三个独立阶段。

## 职责

负责单章或五章以内正文草稿生成、逐章总结与状态提交、用户主动触发的正文自然化，以及按连续五章执行的后置审查与修复。普通生产链为：正文生成 → 生成稿候选验证 → 总结/状态回证 → 逐章提交 → 继续创作；手动自然化链为：用户明确触发 → 创建表达修订 attempt → 候选验证 → 修订提交。通用自然化规则只存在于 `prompts/正文自然化提示词.md`；本流程只描述阶段顺序和安全契约，不复制自然化规则。

## 范围限制

- 每个正文生成请求最多 5 章；超过 5 章时要求拆分创作请求。
- 每个审查或修复子批恰按连续最多 5 章执行；目标范围超过 5 章时按章节顺序自动拆成多个子批，不把多章合成一份审查证据。
- “继续写”但未指定范围时，默认处理下一章或下一组最多 5 章。
- 每章都必须单独组装上下文，不能把上一章的整份上下文直接复用；前一章完成逐章提交后，下一章从 current head 的正式正文、总结和状态仓库继续。

## 默认创作与审查编排

普通写作和续写只跑创作链，不询问是否先审查，也不自动补审历史章节：

1. 按章节顺序生成并验证当前章候选，不自动执行自然化。
2. 立即从最终候选生成章节总结、主角状态增量和需要的系统/经营状态增量，执行独立状态回证。
3. 状态回证通过后，按章 prepare、CAS commit 和物化，把该章标记为 `review_pending`；此时正文、章节总结、主角状态仓库、系统状态仓库和章节序列已经同步，但正文文件名仍必须保留 `（草稿）.md`。
4. 下一章重新组装上下文，直接读取新 current head。请求范围写完即结束创作任务，不自动转入审查。
5. 历史 `review_pending` 节点不阻断续写。历史遗留且尚未提交的合法 attempt，则先补齐总结、状态回证并逐章提交为 `review_pending`，不先做正式审查。

用户明确要求审查后，选择连续章节，按每 5 章一个子批执行。一章两份独立报告，不能用一份总报告代替。当前可见正文与 committed 哈希一致时走严格正式审查；不一致时默认审查用户当前能看到的文件，走显式工作副本模式并保留 committed 版作为比较基线，不能把旧哈希报告当成当前稿放行。纯“审查”只报告问题，只有“审查并修复”或等价指令才进入修复。

## 一、正文生成

### 执行步骤

1. 解析章节范围。
2. 按 `references/长篇上下文与一致性.md` 组装每一章上下文。
3. 执行写前大纲-上下文校准闸门。
4. 采用文风系统的项目，执行文风校准闸门：
   1. 项目配置为 `已确认` 或 `已冻结` 时，项目文风文件必须存在且版本一致。
   2. 本章场景模式必须能映射到项目文风规范。
   3. 若项目文风与角色规格卡冲突，明确采用角色规格卡。
   4. 若项目文风要求会导致大纲外扩写，放弃该要求，不新增事件。
   5. 生成时只输出正文；不得在正文后附“风格执行自查”。
5. 读取 `prompts/正文生成提示词.md`。
6. 按章节顺序逐章生成正文。
7. 每写完一章，立即运行 `scripts/count_chars.py <正文文件>`，按审查口径取得实际字数。创作目标统一为2200-3000字；不足2200字时，只扩写本章大纲已有场景中的动作、对话、因果桥、情绪转折或结果反馈，超过3000字时压缩重复表达和无功能内容，然后重新计数。实际字数进入2200-3000字前，不得更新总结或进入下一章；低于2000字尤其不得放行。
8. 采用文风系统且配置来源范文的项目，运行 `scripts/原文重合检查.py` 检查草稿与来源范文的连续文本重合。重合检查命中阻断阈值时必须局部改写并复查，不能删除大纲核心事件来规避；脚本失败时报告风险，不得声称通过。
9. 字数达标后，把生成稿原样写入 attempt 的 `source.md` 与 `candidate.md`，两者 SHA-256 必须一致；记录 `naturalization_result: not_requested`，生成非空事实锁并运行候选验证。
10. 候选验证通过后直接生成章节总结和状态增量，不调用正文自然化提示词。
11. 创作提交物化到 `正文/第XXX章_章节名（草稿）.md`；提交、总结、状态更新和继续创作都不得移除“草稿”。

### 阻断条件

- 大纲和上下文冲突。
- 同一章存在多个正文文件。
- 本章所需大纲缺失。
- 伏笔原章或关键总结缺失，且该伏笔影响本章逻辑。
- 用户要求的章节范围超过 5 章。
- 采用文风系统时项目文风文件缺失、版本不一致，或本章场景模式无法映射到项目文风规范。

## 二、手动正文自然化

本阶段只在用户明确说“自然化”“去AI”“去除AI味”或等价指令时执行。普通写作、续写、总结、会话结束和审查都不得隐式触发。

1. 读取 `prompts/正文自然化提示词.md`，以目标章当前权威正文作为 `source.md`，保存源正文哈希并创建递增的新 attempt。
2. `naturalization.md` 必须记录 `node_id`、`attempt_id`、`source_sha256`、`candidate_sha256`、`prompt_version`、`processed_at` 和 `naturalization_result`；`fact-lock.json` 必须为非空列表并绑定真实来源锚点。
3. 候选先运行 `scripts/validate_chapter_candidate.py --attempt-dir <attempt> --project-root <项目根>`，再运行 `count_chars.py`。数值、否定极性、事件、角色认知、系统状态或章末结果变化时阻断该候选，不能进入提交或总结回写。
4. 表达已经自然时记录 `naturalization_result: skipped` 且候选与源正文保持字节一致；确有表达修改时记录 `candidate`，不得为了证明执行过而强制换词。
5. 未提交草稿的手动自然化通过验证后，可以用候选继续原创作提交流程。已提交正文的手动自然化属于修订：创建新事务，正文哈希变化使旧审查失效并回到 `review_pending`；已有后续 committed 节点时按 `项目结构与迁移.md` 执行 rebase。
6. 合法自然化只能改变表达。语义总结和状态仓库内容不重算，只更新正文哈希与关联元数据；若候选确实需要改变事实，退出自然化路由，改由用户明确授权的剧情修复流程处理。

## 三、正式草稿审查

### 职责

严格正式审查接收已经提交且审查状态为 `review_pending`、正文哈希仍与 current chain 一致的正文。目标章可能是未经自然化的生成稿，也可能是用户手动自然化后的修订稿；只输出审查报告，不默认修改正文，待审状态不影响后续章节创作。

若 `正文/` 当前可见文件已经被用户或外部工具继续修改，审查对象改为工作副本：新建递增 attempt，以 committed 正文快照作为 `workspace/source.md`，当前文件快照作为 `candidate.md`，记录 `review_subject: working_copy`、`base_committed_sha256`、`working_copy_sha256` 与 `working_copy_path`。这类审查用于判断当前稿是否仍守住事实和上下文，不改变 current chain 的权威状态。

### 审查模式

删除 full/lean/solo 等没有实际 Agent 契约的审查模式。审查统一执行一次"源稿/候选完整性审查（严格模式即自然化前后差异审查）"和一次"候选正文对项目上下文审查"，两次为不同 reviewer 的独立调用，固定写入 `reviews/naturalization.md` 与 `reviews/context.md`，并绑定同一 `reviewed_sha256`。严格模式下，`naturalization_result: not_requested` 时第一份报告只确认源稿与候选字节一致且未运行自然化，随后运行 `validate_chapter_candidate.py --require-reviews`。工作副本模式下，第一份报告比较 committed 基线与当前稿，第二份报告对当前稿重新检查全部 13 维；两份报告都增加 `review_subject: working_copy`、`base_committed_sha256` 和 `working_copy_sha256`，随后运行 `validate_chapter_candidate.py --allow-working-copy --require-reviews`。

工作副本模式允许旧 `source_path` 指向的可见正文发生哈希/措辞漂移，但 `workspace/source.md` 必须仍与 committed 基线哈希一致，每条事实锁必须提供当前稿 `working_copy_anchor`。确定性数值变化仍阻断；否定词数量变化只转为待语义复核警告，`polarity` 维度仍必须通过。事实、事件、角色认知、任务判定和系统边界不得因工作副本模式放宽。

### 审查输入

- 目标正文
- 生成源稿与当前候选；手动自然化时再读取自然化前版本
- 事实锁
- 本章大纲
- 最近 20 章章节总结
- 最近 3 章正文
- 当前阶段总结
- `novel-config.md`
- `总结/主角状态仓库.md`
- 角色档案、伏笔追踪表、写作铁律
- 采用文风系统的项目：`novel-config.md` 文风配置 + `创作依据/文风规范.md` + `创作依据/文风校准记录.md` 当前版本之后仍有效的校准项
- 可用脚本输出

### 逻辑依赖表

审查前必须派生审查逻辑依赖表，且必须包含关键时间锚。至少包含：

- 本章前已经确立的硬事实
- 本章涉及的关键时间锚
- 角色在本章开始前知道什么、不知道什么
- 主角和关键角色当前能力/资源
- 目标章提交前状态、该章正文/章节总结造成的状态增量，以及审查子批内后续章已经承接的事实
- 关系状态
- 信息流边界
- 因果债与未解决冲突
- 后文禁止误写

### 问题分类

- A 类：硬伤，必须修。包括时间线矛盾、角色认知越界、硬事实冲突、能力越级、信息流泄露、伏笔含义变形，以及手动自然化造成的数值/事实/视角/时间线破坏。
- B 类：风险或体验问题。包括节奏拖沓、爽点弱、表达重复、情绪铺垫不足。

### 脚本证据

- 如果 `scripts/count_chars.py` 存在且适用，优先运行脚本。
- 审查报告引用 `count_chars.py` 输出作为字数等量化证据。
- 采用文风系统且配置来源范文的项目，运行 `scripts/原文重合检查.py` 检查连续文本重合；审查报告记录结论和必要位置，临时重合检查报告不进入长期上下文。
- 如果脚本不存在，报告中注明未使用脚本，不临时创建替代脚本。

### 项目文风一致性检查

采用文风系统的项目，正式审查新增独立的“项目文风一致性”检查，与正文生成及可选手动自然化分工。审查只报告具有正文证据和修改价值的偏移：

- 硬规则违反；
- 叙事视角或距离漂移；
- 同类场景连续偏离项目场景模式；
- 角色规格卡被全书文风覆盖；
- 通用模型模板重新出现；
- 与来源范文存在连续文本重合风险。

单个句子没有命中软倾向，不构成问题。不得为了追求统计完全一致，把正文机械修成平均值。审查报告增加：

```markdown
## 文风执行核对
- 项目文风版本：
- 场景模式匹配：通过 / 偏移
- 硬规则：通过 / 违反
- 软倾向整体一致性：稳定 / 轻微漂移 / 明显漂移
- 角色声音优先级：通过 / 被项目文风覆盖
- 原文重合检查：通过 / 需复核 / 阻断
- 证据位置：
```

未采用文风系统的项目不输出该核对块。

### 审查报告

- 审查报告写入对应 50 章归档文件。
- 报告必须明确章节、问题位置、问题类型、前文依据和修复建议。
- A 类问题必须给出“为什么影响后文逻辑”的说明。
- 用户单独要求“只审查”时审查后停止并保持正文不变；只有明确要求“审查并修复”时处理失败项。

## 四、修复

### 触发条件

- 用户明确要求“修复”“审查并修复”“fix”。
- “审查并修复”任务的正式审查发现需要修复的问题。
- 有审查报告，或用户明确指出需要修复的问题。
- 如果用户只说“审查”，只审查不修复。

### 范围限制

- 自动修复一次最多 5 章。
- 超过 5 章必须要求拆分。

### 修复输入

- 目标正文
- 本章大纲
- 审查报告或用户指出的问题
- 写作铁律
- 角色档案
- `总结/主角状态仓库.md`
- 相关章节总结和阶段总结
- 采用文风系统的项目：`novel-config.md` 文风配置 + `创作依据/文风规范.md` + `创作依据/文风校准记录.md` 当前版本之后仍有效的校准项

### 修复顺序

1. 先修 A 类硬伤。
2. 再处理 B 类体验问题。
3. 采用文风系统的项目，再按审查报告的"文风执行核对"处理有正文证据的文风偏移；修复遵守最小修改原则：
   - 只修审查确认的问题段落。
   - 不改变事件、信息、人物选择、时间线和资源结算。
   - 不为了接近统计值批量替换全章句式。
   - 修复角色台词时先服从角色规格卡，再服从项目文风。
   - 若修复需要改变场景结构或事件顺序，标记高风险并停止自动修复，先给用户方案。
4. 每次只改与问题相关的段落。
5. 修改前后运行 `scripts/count_chars.py`，把字数等变化写入修复情况。
6. 采用文风系统且配置来源范文的项目，修复后重新运行 `scripts/原文重合检查.py`，重合检查通过前不得报告完成。
7. 修改后创建新 attempt，重新执行候选验证和两份独立审查；旧正文哈希上的报告全部失效，不能只做局部复查后放行。目标原本就是未入链的当前可见稿时，继续使用工作副本模式，验证通过也只形成工作副本审查证据。
8. 判断修复影响：纯表达修改只更新正文哈希、审查证据和关联元数据；事件、角色认知、数值、资源、关系、系统状态或章末结果发生变化时，重新生成目标章 summary/state delta，并从目标章开始重建受影响的仓库投影。
9. 如果事实性修改影响后续已提交章节的前提、状态或钩子，按 `项目结构与迁移.md` 从第一处影响点 rebase；逐章复核后续正文及总结，不能只改上游章后继续沿用失效投影。
10. 写回归档块时，只替换对应 HTML 锚点块，不覆盖无关章节。
11. 复读正文、审查报告、章节总结和主角状态仓库，确认修改生效且状态链一致。

### 修复确认

- 用户手动修复后说“修好了”“已修复”“修改完毕”时，读取正文和审查报告。
- 核对审查报告中的问题是否已解决。
- 更新审查进度表和章节文件状态。
- 如仍有 A 类问题，不能标记为通过。

### 禁止行为

- 不得为修复一个问题擅自新增主线事件。
- 不得扩大修改范围到无关段落。
- 不得跳过审查报告中的 A 类问题。
- 不得为了修复当前章而改写前文事实。

## 五、生产门禁

与 current chain 哈希一致的已提交正文进入 `review_passed` 前必须通过三项共同门禁：

1. 确定性检查 `scripts/validate_chapter_candidate.py`：核对事实锁 ID、所有受保护数值/实体/系统状态、否定极性标记和文件哈希。
2. 一次"源稿/候选完整性审查"和一次"候选正文对项目上下文审查"，两次为独立模型调用、分别落报告并记录哈希；未请求自然化时第一份只验证字节一致和 `not_requested` 状态。
3. 任一检查或审查失败都不能进入 `review_passed`；因果、指代、动机等高风险项必须在两份报告中同时为 pass。失败只阻断审查通过标记，不自动阻断继续创作。
4. `review_pending` 或任一审查失败时，正文文件名必须保留 `（草稿）.md`。只有本节三项门禁全部通过并完成 `review_passed` 登记后，才允许原子改名为不带 `（草稿）` 的文件名。

工作副本即使通过同样的候选检查和两份审查，也固定为 `eligible_for_review_passed: false`：不改名、不写 attestation、不推进 head、不物化总结/状态仓库。只有用户明确要求正式纳入提交链时，才转入下一节的修订/rebase 流程。

## 六、创作提交与审后回写

创作提交不等待自然化或正式审查。生成稿候选验证通过后生成章节总结和状态增量，状态回证通过后冻结正文、总结、状态资产并推进 commit head；事务记录 `review_status: review_pending`，正文以带 `（草稿）` 的文件名物化。正文、候选、总结和状态更新必须使用同一个稳定章节节点 ID。

后置审查绑定已提交正文 SHA-256。两份报告通过后把该正文哈希标记为 `review_passed`，并在同一审查通过事务中把可见正文从 `第XXX章_章节名（草稿）.md` 原子物化为 `第XXX章_章节名.md`；正文未变化时不重新生成总结或仓库。审查未通过不得改名。审查修复改变正文时必须产生新 attempt 和修订事务，正文哈希变化自动使旧审查失效并恢复带 `（草稿）` 的文件名；是否重算语义总结和状态仓库按修复影响判断。两阶段提交与 commit-head 协议见 `项目结构与迁移.md` 与 `scripts/项目事务.py`。
