# 正文生产与审修

本文是正文生产、自然化、正式审查与修复的唯一流程文档，合并了旧《草稿生成流程》《草稿审查流程》与《草稿修复流程》。

## 职责

负责单章或五章以内正文草稿生成、正文自然化、正式草稿审查与修复。生产链为：正文生成 → 正文自然化 → 正式草稿审查 → 修复与归档。通用自然化规则只存在于 `prompts/正文自然化提示词.md`；本流程只描述阶段顺序和安全契约，不复制自然化规则。

## 范围限制

- 正文创作、自然化、审查与修复一次最多 5 章。
- 超过 5 章必须停止并要求拆分，或等待后续批处理脚本。
- “继续写”但未指定范围时，默认处理下一章或下一组最多 5 章。
- 每章都必须单独组装上下文，不能用上一章上下文直接续写下一章。

## 一、正文生成

### 执行步骤

1. 解析章节范围。
2. 按 `上下文组装.md` 组装每一章上下文。
3. 执行写前大纲-上下文校准闸门。
4. 采用文风系统的项目，执行文风校准闸门：
   1. 项目配置为 `已确认` 或 `已冻结` 时，项目文风文件必须存在且版本一致。
   2. 本章场景模式必须能映射到项目文风规范。
   3. 若项目文风与角色规格卡冲突，明确采用角色规格卡。
   4. 若项目文风要求会导致大纲外扩写，放弃该要求，不新增事件。
   5. 生成时只输出正文；不得在正文后附“风格执行自查”。
5. 读取 `prompts/正文生成提示词.md`。
6. 按章节顺序逐章生成正文。
7. 每写完一章，立即运行 `scripts/count_chars.py <正文文件>`，按审查口径取得实际字数。创作目标统一为2200-3000字；不足2200字时，只扩写本章大纲已有场景中的动作、对话、因果桥、情绪转折或结果反馈，超过3000字时压缩重复表达和无功能内容，然后重新计数。实际字数进入2200-3000字前，不得更新总结或进入下一章；低于2000字尤其不得放行。
8. 采用文风系统且配置来源范文的项目，运行 `scripts/原文重合检查.py` 检查草稿与来源范文的连续文本重合。重合检查命中阻断阈值时必须局部改写并复查，不能删除大纲核心事件来规避；脚本失败时报告风险，不得声称通过。
9. 字数达标后，进入正文自然化阶段（见下）。

### 阻断条件

- 大纲和上下文冲突。
- 同一章存在多个正文文件。
- 本章所需大纲缺失。
- 伏笔原章或关键总结缺失，且该伏笔影响本章逻辑。
- 用户要求的章节范围超过 5 章。
- 采用文风系统时项目文风文件缺失、版本不一致，或本章场景模式无法映射到项目文风规范。

## 二、正文自然化

1. 草稿生成后保存自然化前版本和内容哈希，再生成正文自然化候选。
2. 自然化使用 `prompts/正文自然化提示词.md`；跳过时原因写入审查元数据。
3. 候选进入字数与文件完整性检查（`scripts/validate_chapter_candidate.py` 与 `count_chars.py`）。
4. 自然化候选在通过正式审查前，不得覆盖正文，不得更新总结、状态仓库或章节序列。
5. 每章使用稳定节点 ID 与递增 attempt 号；源稿哈希变化、候选修复或重新自然化都必须新建下一 attempt，不覆盖旧尝试。
6. 自然化前版本、候选、自然化记录与事实锁的 SHA-256 绑定由 `scripts/validate_chapter_candidate.py` 确定性核对；任一哈希变化使旧审查失效，回到 `review_pending`。

## 三、正式草稿审查

### 职责

正式审查接收自然化候选（或显式跳过的源稿）。只输出审查报告，不默认修改正文。

### 审查模式

删除 full/lean/solo 等没有实际 Agent 契约的审查模式。审查统一执行一次"自然化前后差异审查"和一次"候选正文对项目上下文审查"，两次为独立模型调用、分别落报告并记录哈希。

### 审查输入

- 目标正文
- 自然化前版本与自然化候选
- 事实锁
- 本章大纲
- 最近 20 章章节总结
- 最近 3 章正文
- 当前阶段总结
- `novel-config.md`
- `总结/主角状态仓库.md`
- 角色档案、伏笔追踪表、写作铁律
- 采用文风系统的项目：`novel-config.md` 文风配置 + `创作依据/文风规范.md` + `创作依据/文风校准记录.md` 当前版本之后仍有效的校准项
- 可用脚本输出

### 逻辑依赖表

审查前必须派生审查逻辑依赖表，且必须包含关键时间锚。至少包含：

- 本章前已经确立的硬事实
- 本章涉及的关键时间锚
- 角色在本章开始前知道什么、不知道什么
- 主角和关键角色当前能力/资源
- 主角状态仓库中的当前真实状态，以及本章正文/章节总结造成的状态增量
- 关系状态
- 信息流边界
- 因果债与未解决冲突
- 后文禁止误写

### 问题分类

- A 类：硬伤，必须修。包括时间线矛盾、角色认知越界、硬事实冲突、能力越级、信息流泄露、伏笔含义变形、自然化造成的数值/事实/视角/时间线破坏。
- B 类：风险或体验问题。包括节奏拖沓、爽点弱、表达重复、情绪铺垫不足。

### 脚本证据

- 如果 `scripts/count_chars.py` 存在且适用，优先运行脚本。
- 审查报告引用 `count_chars.py` 输出作为字数等量化证据。
- 采用文风系统且配置来源范文的项目，运行 `scripts/原文重合检查.py` 检查连续文本重合；审查报告记录结论和必要位置，临时重合检查报告不进入长期上下文。
- 如果脚本不存在，报告中注明未使用脚本，不临时创建替代脚本。

### 项目文风一致性检查

采用文风系统的项目，正式审查新增独立的“项目文风一致性”检查，不与通用 AI 味检查混为一项。审查只报告具有正文证据和修改价值的偏移：

- 硬规则违反；
- 叙事视角或距离漂移；
- 同类场景连续偏离项目场景模式；
- 角色规格卡被全书文风覆盖；
- 通用模型模板重新出现；
- 与来源范文存在连续文本重合风险。

单个句子没有命中软倾向，不构成问题。不得为了追求统计完全一致，把正文机械修成平均值。审查报告增加：

```markdown
## 文风执行核对
- 项目文风版本：
- 场景模式匹配：通过 / 偏移
- 硬规则：通过 / 违反
- 软倾向整体一致性：稳定 / 轻微漂移 / 明显漂移
- 角色声音优先级：通过 / 被项目文风覆盖
- 原文重合检查：通过 / 需复核 / 阻断
- 证据位置：
```

未采用文风系统的项目不输出该核对块。

### 审查报告

- 审查报告写入对应 50 章归档文件。
- 报告必须明确章节、问题位置、问题类型、前文依据和修复建议。
- A 类问题必须给出“为什么影响后文逻辑”的说明。
- 默认审查后停止，不自动修复。

## 四、修复

### 触发条件

- 用户明确要求“修复”“审查并修复”“fix”。
- 有审查报告，或用户明确指出需要修复的问题。
- 如果用户只说“审查”，只审查不修复。

### 范围限制

- 自动修复一次最多 5 章。
- 超过 5 章必须要求拆分。

### 修复输入

- 目标正文
- 本章大纲
- 审查报告或用户指出的问题
- 写作铁律
- 角色档案
- `总结/主角状态仓库.md`
- 相关章节总结和阶段总结
- 采用文风系统的项目：`novel-config.md` 文风配置 + `创作依据/文风规范.md` + `创作依据/文风校准记录.md` 当前版本之后仍有效的校准项

### 修复顺序

1. 先修 A 类硬伤。
2. 再处理 B 类体验问题。
3. 采用文风系统的项目，再按审查报告的"文风执行核对"处理有正文证据的文风偏移；修复遵守最小修改原则：
   - 只修审查确认的问题段落。
   - 不改变事件、信息、人物选择、时间线和资源结算。
   - 不为了接近统计值批量替换全章句式。
   - 修复角色台词时先服从角色规格卡，再服从项目文风。
   - 若修复需要改变场景结构或事件顺序，标记高风险并停止自动修复，先给用户方案。
4. 每次只改与问题相关的段落。
5. 修改前后运行 `scripts/count_chars.py`，把字数等变化写入修复情况。
6. 采用文风系统且配置来源范文的项目，修复后重新运行 `scripts/原文重合检查.py`，重合检查通过前不得报告完成。
7. 修改后做局部复查。
8. 更新审查报告进度、章节总结和章节文件状态。
9. 如果修复改变主角状态，先在章节总结记录状态增量，再同步 `总结/主角状态仓库.md`。
10. 写回归档块时，只替换对应 HTML 锚点块，不覆盖无关章节。
11. 复读正文、审查报告、章节总结和主角状态仓库，确认修改生效且状态链一致。

### 修复确认

- 用户手动修复后说“修好了”“已修复”“修改完毕”时，读取正文和审查报告。
- 核对审查报告中的问题是否已解决。
- 更新审查进度表和章节文件状态。
- 如仍有 A 类问题，不能标记为通过。

### 禁止行为

- 不得为修复一个问题擅自新增主线事件。
- 不得扩大修改范围到无关段落。
- 不得跳过审查报告中的 A 类问题。
- 不得为了修复当前章而改写前文事实。

## 五、生产门禁

正文候选进入 `review_passed` 前必须通过三项共同门禁：

1. 确定性检查 `scripts/validate_chapter_candidate.py`：核对事实锁 ID、所有受保护数值/实体/系统状态、否定极性标记和文件哈希。
2. 一次"自然化前后差异审查"和一次"候选正文对项目上下文审查"，两次为独立模型调用、分别落报告并记录哈希。
3. 任一检查或审查失败都不能进入 `review_passed`；因果、指代、动机等高风险项必须在两份报告中同时为 pass。

## 六、两阶段事务提交

审查通过后才允许生成待提交的章节总结和状态快照；生成总结前、事务 prepare 前和最终 commit 前都必须确认正文 SHA-256 等于审查哈希。正文、候选、审查、总结和状态更新必须使用同一个稳定章节节点 ID。两阶段提交与 commit-head 协议见 `项目结构与迁移.md` 与 `scripts/项目事务.py`。
