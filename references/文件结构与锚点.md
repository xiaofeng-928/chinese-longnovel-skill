# 文件结构与锚点

## 共享长篇范文库

长篇范文库不属于单本小说项目，标准根目录为 `D:\ai小说\小说\范文`，按 `范文\<平台>范文\<大类题材>\《作品名》` 组织。作品目录中的 `元数据.md`、合法导入的 `正文.txt`、`章节索引.md` 和 `拆书报告.md` 按 `范文与创作依据.md` 维护；执行文风蒸馏后还会生成 `文风统计报告.md`、`文风分析报告.md` 和 `文风基因.md`，按 `范文与创作依据.md` 维护；细分题材不建目录。

范文文风的证据权威是 `正文.txt` + `章节索引.md` + `文风统计报告.md`，范文抽象文风资产是 `文风基因.md`。拆书报告负责"写了什么、为什么有效"，文风分析报告负责"语言如何运行"，两者互不替代。

使用范文的单本项目在根目录维护 `参考素材.md`，在 `plan/范文迁移方案.md` 维护原创迁移决策。两者是大纲输入，不得替代 `novel-config.md`、总大纲或分阶段细纲。

## 职责

负责小说项目目录结构、文件命名、50章归档、阶段总结定位、HTML 锚点和安全替换规则。

## 标准项目结构

```text
小说项目/
├── novel-config.md
├── 参考素材.md                         # 使用范文时已有
├── 文风/                                # 采用文风系统时
│   ├── 项目文风规范.md                 # 唯一执行权威
│   └── 文风校准记录.md                 # 首次偏移或版本变化时创建
├── plan/
│   └── 金手指发展_第X-Y章.md（复杂金手指或本阶段有明显变化时）
├── 正文/
├── 总结/
│   ├── 主角状态仓库.md
│   └── 系统状态仓库.md（达到拆分条件时可选）
├── 审查报告/
└── 修复记录/
```

没有采用文风系统的旧项目不创建空 `文风/` 目录。`文风/项目文风规范.md` 是当前项目唯一可执行的文风权威源，正文生成、审查和修复只读取它，不得加载范文正文或带例证的分析报告。

`plan/` 存放总大纲、黄金三章细纲和 50 章归档细纲。复杂金手指还按50章窗口维护 `plan/系统发展_第X-Y章.md`，它是资源预算、系统商店、主角经营商店、阶段任务池、成长路线和五章玩法循环的计划态；如果旧项目仍使用“大纲/”，先按现有项目目录执行，不得擅自搬迁文件。

`plan/章节序列.md`（或按项目现有 50 章分块拆分的同名文件）记录主线、手动插入和支线节点的有效阅读顺序。括号编号如 `第49(1)章` 保持现有正文命名格式，并通过章节序列决定是否参与上下文。

## 章节文件命名

`总结/` 是总结的唯一标准根目录：章节总结和阶段总结均写入该目录下按项目既有命名的 50 章归档或阶段文件；主角当前真实状态统一维护在 `总结/主角状态仓库.md`。复杂金手指达到拆分条件时，可建立 `总结/系统状态仓库.md` 维护完整系统运行态，主角仓库只保留摘要和链接。总大纲只维护计划状态，章节总结只维护状态增量与证据，完整当前状态以对应仓库为准。`章节总结/`、`阶段总结/` 仅作为旧项目兼容名称；新建项目不得同时创建多个总结根目录。

- 正文章节文件使用第几章和状态标签命名。
- 正文生成后进入自然化阶段并保存自然化前版本与哈希；未审查的正文保持 `（草稿）` 标签，审查后按审查结论更新状态标签，不得伪装成“已审查”或正式稿。
- 同一章出现多个正文文件时必须停止，并让用户确认哪个是权威版本。
- 不得擅自删除、覆盖或合并同章冲突文件。
- 用户手动修复后确认“修好了”“已修复”“修改完毕”时，再根据审查报告和复读结果更新状态标签。

## 50章归档

- 大纲、章节总结、审查报告、修复记录按 50 章一个归档文件管理。
- 第 1-50 章归入第一个分块，第 51-100 章归入第二个分块，以此类推。
- 一次只处理 5 章正文、审查或修复，不改变 50 章归档规则。
- 不要因为一次只处理 5 章就新建 5 章文件。

## 阶段总结定位

- 阶段总结是长期记忆层。
- 阶段总结文件按 `novel-config.md` 中的阶段划分定位。
- 阶段总结必须包含 `关键时间锚`。
- 阶段总结只记录阶段结算和仓库核对快照，不另建完整主角状态表；完整当前状态以 `总结/主角状态仓库.md` 为准。

## HTML 锚点

- 章节大纲、章节总结、审查报告、修复记录都使用稳定 HTML 注释锚点包裹。
- 重生成、重审、重修时，只替换目标锚点块。
- 不得重复追加同一锚点块。
- 不得覆盖同一 50 章归档文件里的无关章节块。
- 修改后必须复读归档文件，确认目标块被替换且相邻章节块未损坏。

## `novel-config.md` 字段

- 基本信息：书名、类型、题材、卖点、主角、主线目标。
- 阶段划分：阶段名、章节范围、阶段目标。
- 写作铁律：节奏、视角、禁用写法、爽点规则。
- 能力表现边界：系统/金手指/力量体系/特殊技能允许怎样外显、哪些视觉和台词禁写、外人认知边界、对外解释口径。非玄幻主类型必须明确“不得写成玄幻世界观视觉”。
- 金手指设计档案：特殊能力的初始功能、运行闭环、货物/资源池、进货/获取方式、交易/变现方式、成本收益、限制代价、升级树、信息流边界和阶段演化。它与能力表现边界并列，负责“怎么运行和发展”；能力表现边界只负责“怎么外显和解释”。
- 金手指阶段规划：`plan/系统发展_第X-Y章.md` 负责“本阶段打算怎样发展”，不能覆盖已经发生的运行状态。
- 主角状态仓库：当前章节已经发生的主角身份、位置、能力、资源、身体、关系、认知、目标、剧情债务、名声和后文禁止误写；标准路径为 `总结/主角状态仓库.md`。
- 系统状态仓库：达到复杂度阈值时在 `总结/系统状态仓库.md` 维护已发生的余额、任务、双商店、属性、模块、冷却、债务和战损；未拆分时这些字段仍由主角仓库维护。
- 角色档案：身份、关系、目标、认知边界、能力边界、性格规格卡。
- 伏笔追踪表：伏笔、埋设章、预计回收章、当前状态。
- 世界观设定：规则、限制、资源、势力。

## 文风配置

采用文风系统的项目，`novel-config.md` 必须增加 `## 文风配置` 字段：

```markdown
## 文风配置

- 文风状态：待选择 / 已确认 / 已冻结 / 待校准
- 文风模式：单范文 / 多范文融合 / 无范文原创
- 项目文风文件：文风/项目文风规范.md
- 文风版本：v1.0
- 生效章节：第1章
- 来源范文：无 / 范文路径列表
- 目标平台：番茄 / 起点 / 其他
- 核心叙事口径：一句话摘要
- 文风变更规则：变更必须新建版本并记录生效章节，不追溯改写既有正文
```

完整句法参数、场景模式和禁用规则不得重复写入 `novel-config.md`，它们只存在于 `文风/项目文风规范.md`。文风版本变更必须递增版本号、在 `文风/文风校准记录.md` 记录原因和差异、写明新版本生效章节，默认不追溯重写旧章节。

## 细纲记忆同步

- 分阶段细纲生成并审查通过后，必须把"细纲记忆同步清单"写回权威记忆层，不能只留在 50 章细纲归档里。
- `novel-config.md` 是角色、能力与金手指设计的唯一权威源；同范围 `plan/系统发展_第X-Y章.md` 是金手指阶段计划权威；`总结/主角状态仓库.md` 是主角当前真实状态的唯一当前状态权威源，若已拆分则 `总结/系统状态仓库.md` 是完整金手指运行态的唯一当前状态权威源。设计、计划、运行不得互相覆盖，也不得在两个仓库重复维护完整数值。
- 采用文风系统的项目，`文风/项目文风规范.md` 是当前执行文风的唯一权威源；`novel-config.md` 只保存文风入口、状态、版本、生效章节和核心约定，不复制完整规范。
- 总大纲文件通常位于 `plan/` 目录；优先使用 `总大纲.md`，若不存在则使用项目已有的总大纲文件。总大纲不是角色卡副本，只承载阶段目标、主线/反派线、伏笔追踪、重大退出和下阶段铺垫，并且只在宏观剧情结构变化时更新。
- 对已有角色只增补缺失画像或强化约束，不重写已稳定设定；若细纲新设定与原设定冲突，停止并让用户确认。
- 写回后必须复读 `novel-config.md` 和对应细纲归档；若同步清单包含宏观剧情结构变化，还必须复读总大纲，确认同步项已经落入正确的权威记忆层。
- 主角状态仓库必须在每章总结落盘后同步，并复读仓库和章节总结；章节总结只保留状态增量与证据，不复制完整仓库。

## 已下线角色压缩

- 第51-100章细纲审查通过后，执行一次前段角色清理：检查第1-50章归档中的前48章大纲，并把第49-50章作为边界未写章节细纲组装；第49-50章若尚未落地正文，只作为计划事实。
- 仅处理已死亡/已下线角色：必须是已死亡，或确认永久退出主线且后续不再处理的角色。
- 保留未死亡角色：入狱、远走、败退、被雪藏、暂时离场但未来仍有镜头的角色，原角色卡保持不动。
- 对确认压缩的角色，将上下文压缩为"已死亡"，并标记"已死亡、已下线"；后续章节不再按活跃角色处理。
- 保留该角色核心三项性格，用于主角、反派或旁人后续评价与回忆。
- 移除“绝对不能写什么”、行动边界、对话禁忌、能力边界等针对活人的限制规则。

## 写入规则

- 写入前先确认目标文件路径。
- 写入归档文件时，只替换对应 HTML 锚点块。
- 如果目标锚点不存在，可以新增目标章节块；但不得影响其他章节。
- 如果检测到重复锚点，停止并报告。
