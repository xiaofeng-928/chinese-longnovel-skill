# 长篇上下文与一致性

本文是正文生成、续写、审查、修复与一致性检查的唯一上下文协议。

## 有效节点

有效正文节点必须同时满足：

1. 节点使用稳定 `node_id`，并存在于 `MYNOVEL:PLAN-NODE` 与章节序列投影中。
2. 对应 transaction 从当前 `commit-head.json` 沿 `parent_transaction_id` 可达，最终抵达 `tx-genesis`。
3. transaction 的 project ID、manifest 哈希、资产快照哈希、双审查证据和状态回证全部通过。
4. transaction 属于 current generation；maintenance rebase 的 shadow 链在原子切换前不进入上下文。

未审查 attempt、孤儿 transaction、`正文/` 中未被 current head 引用的文件、自然化候选和待修复稿都不是有效节点。不得再用“只要正文文件存在就有效”，也不得以“第49(1)章”等显示文件名替代稳定 node ID。

## 组装顺序

每章独立组装：

1. 读取 `novel-config.md`、current commit head、当前计划节点和后续 2 个 main 节点边界。
2. 从 current head 的投影读取 `总结/主角状态仓库.md`；复杂系统项目再读取 `总结/系统状态仓库.md`。仓库是当前真实状态权威源，但必须可由 current 链重建。
3. 读取当前 `plan/系统发展_第X-Y章.md`，只确认允许的任务、商品、预算、成长和经营循环，不把计划当事实。
4. 读取最近 3 个有效节点正文；若没有主线锚点，再补最近 1 个 main 节点。
5. 读取最近 20 个有效节点章节总结，跨 50 章分块拼接并包含上述正文对应总结。
6. 读取 50 章阶段总结；每跨 200 章补读一份长期摘要。长期摘要只保留阶段结算、关键时间锚、仍活跃角色、未偿因果债、伏笔和状态仓库校验点。
7. 补读角色档案、世界观、伏笔追踪、项目文风规范；涉及早期伏笔时补读埋设原章及其总结。

上下文组装后提炼“本章文风执行表”，只保留当前版本、场景模式、硬规则、相关软倾向、角色声音覆盖和高风险表达。禁止把范文 `正文.txt`、拆书原句、文风分析报告中的例句和非 current generation 资产放进正文上下文。

## 逻辑依赖表与事实锁

写作或审查前，把上述上下文压缩为事实锁，至少包含：硬事实、时间锚、角色认知、能力与资源、系统权限/余额/库存、任务感知与判定、双商店分账、关系承诺、信息流、因果债、伏笔和后文禁止误写。每条事实锁记录来源相对路径、原文锚点和 SHA-256；来源改变后旧 attempt 失效。

## 写前闸门

- 本章细纲与 committed 事实冲突时停止，不顺着计划改写历史。
- 不新增细纲外主线事件、角色、能力、设定、任务、商品、货源、支付方式或伏笔。
- 系统阶段计划缺失时退回上游规划；不能在正文中补系统设计。
- 角色认知、称谓、时间传播、资源消耗和关系变化必须有来源或因果桥。
- 采用文风系统时读取 `创作依据/文风规范.md`；角色声音优先于通用文风，文风不得改变事件和数值。

## 续写定位

“继续写/续写”从 current head 的最后 committed main 节点确定下一 planned main 节点，不按目录最大数字或修改时间推断。同一 node ID 有多个权威正文投影时停止。

## 一致性检查

以 current head 链为证据，核对：

- 硬事实、时间线、死人/退出角色、角色认知和信息传播。
- 主角状态仓库中的能力成长、资源资产、身体装备、关系承诺、信息认知、目标债务与后文禁止误写。
- 系统设计、阶段计划和系统状态仓库分层；计划解锁不能冒充当前已获得。
- 任务是否存在可信感知、触发、接受/拒绝、判定、奖励预算和失败后果；阻断全知任务、救场任务、追溯奖励、判定漂移和木偶驱动。
- 系统商店与主角经营商店的库存、价格、订单、利润和转换规则是否分账。
- 伏笔是否超期、变义或提前消费，因果债和关系是否无过渡回退。

章节总结只核对状态增量，不替代仓库。正文与投影冲突时从 committed 正文证据重建投影，不用投影覆盖正文。输出只分“硬伤、风险、伏笔状态、通过项”，每个硬伤给出证据位置和修复方向。
