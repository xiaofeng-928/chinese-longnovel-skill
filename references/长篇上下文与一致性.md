# 长篇上下文与一致性

> 本文合并旧《上下文组装》《章节序列》《一致性检查》，是正文生成、续写、审查、修复前上下文范围与跨章节一致性检查的唯一说明层。本章节顺序以本文的"有效节点组装"为准；旧的"按数字回退"表述不得覆盖有效章节序列规则。

## 一、有效章节序列

### 目的

记录正文创作的实际阅读顺序，解决插入章节、支线章节和主线章节混排时不能按章节数字计算上下文的问题。

### 节点字段

| 字段 | 取值 |
|---|---|
| 节点编号 | `第49章`、`第49(1)章` 等现有命名 |
| 类型 | 主线、手动插入、支线 |
| 主线锚点 | 是/否 |
| 正文状态 | 未开始、已写出未审查、已审查、已修复、废弃 |
| 细纲状态 | 已整理的正式细纲 |

只有正文文件存在且节点未标记为废弃时，节点才是有效正文节点。已写出但未审查的正文仍然有效。

## 二、有效节点组装（现行规则）

- `plan/` 中已写入的细纲均视为正式细纲，直接读取，不区分草稿或候选状态。
- 正文只要文件已经写出就进入有效节点；"已写出未审查"仍必须读取。
- 先在 `章节序列.md` 定位当前节点，再从当前节点之前筛选未废弃的有效节点。
- 读取最近 3 个有效节点正文；若其中不含主线锚点，再补读最近 1 个“主线锚点”的有效节点正文。
- 读取最近 20 个有效节点章节总结，并去重；最近 3 个正文对应总结必须包含。
- 读取当前节点正式细纲，以及后续 2 个主线节点的边界细纲。
- 支线或手动插入节点不因"支线"标签被排除；它是否进入上下文由有效状态决定，是否作为回溯锚点由"主线锚点"字段决定。

例如写第50章时，若前序为第49(1)、第49(2)、第49(3)，且最近主线锚点是第48章，则正文上下文读取四个节点：第49(1)、第49(2)、第49(3)、第48章，而不是按数字回退计算。

## 三、职责

负责正文生成、续写、正式审查、自动修复前必须读取的上下文层级，以及跨章节、跨阶段的一致性检查。上下文虽按项目文风与自然化规则处理表达，仍必须读取事实锁所需的上下文，避免写作或修复时误改时间、资源、认知或系统状态。

## 四、必读上下文

- `novel-config.md`
- `总结/主角状态仓库.md`：先读取，作为主角截至当前有效章节的当前真实状态
- `总结/系统状态仓库.md`：存在时必须读取，作为完整系统运行态；不存在时从主角状态仓库读取系统动态状态
- 当前范围 `plan/系统发展_第X-Y章.md`：存在复杂系统或阶段明显变化时必须读取，只作为本阶段计划，不覆盖运行态
- 当前阶段总结和所有必要的前置阶段总结
- 最近 3 章正文全文
- 最近 20 章章节总结，且必须包含最近 3 章正文对应总结
- 本章完整大纲
- 后续 2 章边界大纲
- 角色档案、写作铁律、能力表现边界、伏笔追踪表
- `novel-config.md` 的文风配置 + `创作依据/文风规范.md` + 当前版本之后仍有效的 `创作依据/文风校准记录.md` 校准项：采用文风系统时必须读取；未采用文风系统不读取

上下文组装顺序必须是：先读取仓库，即先读取 `总结/主角状态仓库.md`，如存在再读取 `总结/系统状态仓库.md` 得到当前快照；随后读取同范围系统阶段规划确认本章允许的任务、商品、成长和预算；最后读取最近章节总结中的状态增量和正文证据核对快照。阶段规划不能替代仓库，也不能把仓库中没有证据的计划状态当成事实。

## 五、文风上下文边界

采用文风系统的项目，正文生成、正式审查和自动修复前必须读取：

- `novel-config.md` 的文风配置；
- `创作依据/文风规范.md`；
- `创作依据/文风校准记录.md` 中当前版本之后仍有效的人工校准项，如文件存在。

上下文组装时提炼一个"本章文风执行表"，只包含：

- 当前文风版本；
- 本章场景模式；
- 适用硬规则；
- 最相关的软倾向；
- 角色说话方式覆盖项；
- 本章高风险表达；
- 禁止加载的来源文件确认。

禁止把范文 `正文.txt`、`文风分析报告.md` 中的原文例证或来源作品的独特表达拼入创作上下文，也不得加载范文文风基因代替 `创作依据/文风规范.md`。采用文风系统的项目，正文阶段只读取项目文风规范；未采用文风系统的项目继续沿用自然化与审查流程，不读取文风文件。

## 六、能力表现边界

- 如果 `novel-config.md` 中存在 `能力表现边界`、`力量表现边界`、`金手指表现边界` 或同义章节，必须完整读取并纳入上下文。
- 如果小说存在系统、异能、修真、武道、真气、丹药、法术、灵力、预知、外挂、血脉、传承等超常能力，但 `novel-config.md` 未写能力表现边界，必须在逻辑依赖表中标注"能力表现边界缺失"，并按小说类型保守处理。
- 对都市、悬疑、现实、商战、刑侦、职场等非玄幻主类型，超常能力只能作为主角内部辅助或专业技能外化，不得写成玄幻世界观视觉；对外解释必须落在职业知识、证据链、规则流程、仪器检测、经验判断、训练成果等本类型可接受框架内。
- 对玄幻、仙侠、奇幻等允许超自然外显的类型，也必须按本书 `能力表现边界` 控制等级、视觉尺度、外人认知和信息流。

## 七、伏笔补读

- 如果本章涉及早期伏笔，必须补读伏笔埋设原章正文。
- 同时补读该章章节总结。
- 只补读与本章逻辑相关的伏笔，不扩大到无关章节。

## 八、逻辑依赖表

组装上下文后，先提炼逻辑依赖表，再进入正文、审查或修复。逻辑依赖表同时用作生成阶段的"事实锁"依据，但不得借机修正大纲或创造新剧情。

逻辑依赖表必须包含：

- 硬事实
- 关键时间锚
- 角色认知
- 主角状态仓库中的当前真实状态
- 章节总结中的状态增量与对应正文证据
- 能力/资源状态
- 系统设计、同范围阶段计划与当前运行态的对应关系
- 系统商店和主角经营商店的当前状态、转换规则与证据
- 系统任务的感知来源、触发条件、接受/拒绝、完成判定、奖励预算与当前任务状态
- 能力表现边界
- 关系状态
- 信息流边界
- 时间锚与信息传播链
- 角色称谓与辈分
- 因果债
- 后文禁止误写

## 九、写前校准闸门

- 对照本章大纲和上下文硬事实。
- 先对照主角状态仓库确认主角当前身份、能力、资源、身体、关系、认知、目标和剧情债务，再对照最近章节总结的状态增量。
- 如果大纲与已发生正文冲突，停止并报告冲突点。
- 总大纲只提供计划状态，不能覆盖主角状态仓库中的实际状态；仓库与正文证据冲突时停止并先修正仓库/总结。
- 不得为了顺着大纲而改写既有事实。
- 不得擅自新增主线事件、角色、能力、设定或伏笔。
- 不得擅自新增阶段规划外的任务、系统商品、经营货源、支付方式、加点路线或模块；若本章细纲依赖这些内容而规划缺失，停止正文生成并退回系统阶段规划。
- 如果本章依赖法务、监管、媒体、跨城交通、抢救、检测、调查、舆论发酵或家族传讯，必须核对时间锚和信息传播链是否足以支撑角色行动。
- 如果本章涉及高频角色、老人/晚辈、家族内斗、师承门派或正式职务称谓，必须核对角色卡中的称谓、辈分和说话方式。

## 十、续写定位

- 用户说"续写""继续写""接着写"但未指定章节时，先定位当前已完成正文后的下一章。
- 定位后仍按正文生成流程处理，不跳过上下文组装。
- 如果同一章有多个正文文件，停止并让用户确认。

## 十一、一致性检查

### 检查输入

- 全部阶段总结
- 最近 3 章正文
- 最近 20 章章节总结
- `总结/主角状态仓库.md`（主角当前真实状态唯一当前状态权威源）
- `总结/系统状态仓库.md`（存在时作为完整系统运行态权威源）
- 当前范围 `plan/系统发展_第X-Y章.md`（存在复杂系统时）
- `novel-config.md`
- 伏笔追踪表
- 相关伏笔原章正文

### 检查项

- 死人复活或退出角色无故回归
- 能力越级或资源凭空出现
- 关系状态回退
- 伏笔超期或含义变形
- 时间线矛盾
- 重复设定或设定冲突
- 前文证据冲突
- 角色认知越界
- 信息流泄露
- 因果断裂
- 系统设计档案、同范围阶段规划和当前状态仓库分层冲突；计划不能冒充已发生状态，正文也不能创造计划外机制
- 系统商店与主角经营商店混账，或商品、价格、库存、订单、利润及二者转换缺少连续记录和正文证据
- 系统任务缺少可解释的感知来源、触发条件、接受/拒绝、判定、时限、奖励预算或失败后果；重点检查全知任务、救场任务、追溯奖励和判定漂移
- 系统选择没有机会成本与场景化结果，任务把主角降为只执行指令的木偶

### 主角状态仓库核对

- 以 `总结/主角状态仓库.md` 的当前真实状态为基线，逐项核对最近正文和章节总结中的状态增量；章节总结只核对状态增量，不替代仓库。
- 核对能力成长、资源资产、身体装备、关系承诺、信息认知、目标债务、名声反馈是否都有正文证据，且没有凭空增加、回退或遗失。
- 核对仓库的"后文禁止误写"是否被当前章节触发；若正文与仓库冲突，先回溯原章证据并修正状态链，再继续写作或审查。
- 系统的等级、权限、库存/额度、货物和消耗必须同时符合 `novel-config.md` 的系统设计档案与仓库动态状态；计划中的解锁不能当作当前已获得。
- 已拆分时，完整系统运行态只以 `总结/系统状态仓库.md` 为准，主角仓库只能保留摘要链接；发现双重完整数值时先消除双重权威。

### 时间线检查

- 优先读取阶段总结中的 `关键时间锚`。
- 对会影响行动逻辑的交通、等待、期限、倒计时、治疗、约定等时间进行交叉核对。
- 如果章节正文中的时间描述与阶段总结关键时间锚冲突，列为 A 类硬伤。

### 输出格式

- 硬伤：必须修。
- 风险：需要确认。
- 伏笔状态：列出未回收和异常伏笔。
- 通过项：简短列出已核对无问题的关键项。

只输出可操作报告，不写泛泛评价。
