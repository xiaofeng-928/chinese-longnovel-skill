# 长篇上下文与一致性

本文是正文生成、续写、审查、修复与一致性检查的唯一上下文协议。

## 有效节点

有效正文节点必须同时满足：

1. 节点使用稳定 `node_id`，并存在于 `MYNOVEL:PLAN-NODE` 与章节序列投影中。
2. 对应 transaction 从当前 `commit-head.json` 沿 `parent_transaction_id` 可达，最终抵达 `tx-genesis`。
3. transaction 的 project ID、manifest 哈希、资产快照哈希和状态回证全部通过；正式审查状态可以是 `review_pending` 或 `review_passed`。
4. transaction 属于 current generation；maintenance rebase 的 shadow 链在原子切换前不进入上下文。

未提交 attempt、孤儿 transaction、`正文/` 中未被 current head 引用的文件、哈希失效候选和待修复稿都不是有效节点。不得再把“尚未审查”等同于“尚未提交”：current head 可达、状态回证通过且投影匹配的 `review_pending` 正文是有效创作事实，可以进入续写上下文。也不得以“第49(1)章”等显示文件名替代稳定 node ID。

## 待审节点

`review_pending` 与 `review_passed` 都是 committed 节点；差别只在是否具备与当前正文哈希匹配的两份正式审查证据：

1. 普通续写读取两者的正文、章节总结和状态仓库，不因待审状态停止或先补审。
2. 正式审查只按连续章节每 5 章分组，不改变节点的创作顺序。
3. 审查报告绑定正文哈希；正文被修订后旧报告自动失效，节点回到 `review_pending`。
4. 事实性修复影响后续节点时，从第一处受影响节点重建 current generation；未受影响节点不因审查标签变化而重新总结。
5. 历史遗留的未提交 attempt 若候选验证已通过，普通续写先补齐总结、状态回证和创作提交，不先执行正式审查。

## 工作副本审查

用户可能在提交后把 `正文/` 拉到外部继续改写。当前可见文件与 current chain 正文哈希不一致时，不把它伪装成有效节点，也不因路径哈希漂移直接终止审查；按以下协议建立独立工作副本证据：

1. 从 current chain 的不可变事务资产取得该章 committed 正文，写入新 attempt 的 `workspace/source.md`；当前可见正文只作为 `candidate.md` 与 `working_copy_path` 指向的审查对象。
2. `naturalization.md` 记录 `review_subject: working_copy`、`base_committed_sha256`、`working_copy_sha256` 和 `working_copy_path`。严格提交候选与工作副本不得共用同一个 attempt。
3. 原事实锁继续绑定 committed 基线；若旧 `source_path` 指向已变化的 `正文/` 文件，只要 `workspace/source.md` 的哈希和原锚点仍闭合，记为锚点漂移警告，不判事实锁来源失效。每条锁另写当前稿 `working_copy_anchor` 及其 SHA-256；稳定的 `expected_value` 必须同时存在于原锚点和当前锚点，供审查核对。
4. 哈希漂移告警不等于事实通过。受保护数字和单位仍做确定性比较；事实、事件、否定极性、角色认知、信息流、任务感知/判定和系统边界必须在两份独立审查中重新检查。原锚点措辞消失但事实等价时允许重新锚定；事实或数值实际变化时相应维度必须 fail。
5. 两份独立审查完成后使用 `validate_chapter_candidate.py --allow-working-copy --require-reviews`；不带 `--require-reviews` 的工作副本验证直接失败。验证结果固定标记 `eligible_for_review_passed: false`；工作副本报告不能去掉“草稿”、生成 attestation、推进 commit head、更新 current 状态仓库或成为续写事实。
6. 用户随后明确要求把工作副本纳入正式链时，才按 committed 正文修订流程判断纯表达修订或事实性修订，并在存在后续 committed 节点时执行 rebase。

## 组装顺序

每章独立组装：

1. 读取 `novel-config.md`、current commit head、当前计划节点和后续 2 个 main 节点边界。
2. 从 current head 的投影读取 `总结/主角状态仓库.md`；复杂系统项目再读取 `总结/系统状态仓库.md`。仓库是当前真实状态权威源，但必须可由 current 链重建。
3. 读取当前 `plan/系统发展_第X-Y章.md`，只确认允许的任务、商品、预算、成长和经营循环，不把计划当事实。
4. 读取最近 3 个有效节点正文，不区分 `review_pending` 与 `review_passed`；若 committed 历史没有主线锚点，再补最近 1 个 committed main 节点。
5. 读取最近 20 个有效节点章节总结，跨 50 章分块拼接并包含上述正文对应总结。
6. 读取 50 章阶段总结；每跨 200 章补读一份长期摘要。长期摘要只保留阶段结算、关键时间锚、仍活跃角色、未偿因果债、伏笔和状态仓库校验点。
7. 补读角色档案、世界观、伏笔追踪、项目文风规范；涉及早期伏笔时补读埋设原章及其总结。

上下文组装后提炼“本章文风执行表”，只保留当前版本、场景模式、硬规则、相关软倾向、角色声音覆盖和高风险表达。禁止把范文 `正文.txt`、拆书原句、文风分析报告中的例句和非 current generation 资产放进正文上下文。

## 逻辑依赖表与事实锁

写作或审查前，把上述上下文压缩为事实锁，至少包含：硬事实、时间锚、角色认知、能力与资源、系统权限/余额/库存、任务感知与判定、双商店分账、关系承诺、信息流、因果债、伏笔和后文禁止误写。每条事实锁记录来源相对路径、原文锚点、SHA-256 和非空 `expected_value`；该值应是候选必须原样保留的稳定事实 token，并同时出现在来源锚点和候选中。允许同义改写、无法用稳定 token 表达的语义事实交给两份独立审查，不伪装成确定性锁。严格提交候选的来源变化会使旧 attempt 失效；工作副本模式按上节保留不可变 committed 基线并重新锚定当前稿，不把可变 `正文/` 路径的哈希漂移本身当成事实变更。

## 写前闸门

- 本章细纲与 committed 事实冲突时停止，不顺着计划改写历史。
- 不新增细纲外主线事件、角色、能力、设定、任务、商品、货源、支付方式或伏笔。
- 系统阶段计划缺失时退回上游规划；不能在正文中补系统设计。
- 角色认知、称谓、时间传播、资源消耗和关系变化必须有来源或因果桥。
- 采用文风系统时读取 `创作依据/文风规范.md`；角色声音优先于通用文风，文风不得改变事件和数值。

## 续写定位

普通“继续写/续写”直接从 current head 的最后 committed main 节点确定下一 planned main 节点，`review_pending` 不触发补审。存在历史遗留未提交 attempt 时，只完成总结、状态回证和创作提交后继续。任何模式都不按目录最大数字或修改时间推断；同一 node ID 有多个候选时只接受最新且通过验证的 attempt，同一 node ID 有多个权威正文投影时停止。

## 一致性检查

以 current head 链为证据，核对：

- 硬事实、时间线、死人/退出角色、角色认知和信息传播。
- 主角状态仓库中的能力成长、资源资产、身体装备、关系承诺、信息认知、目标债务与后文禁止误写。
- 系统设计、阶段计划和系统状态仓库分层；计划解锁不能冒充当前已获得。
- 任务是否存在可信感知、触发、接受/拒绝、判定、奖励预算和失败后果；阻断全知任务、救场任务、追溯奖励、判定漂移和木偶驱动。
- 系统商店与主角经营商店的库存、价格、订单、利润和转换规则是否分账。
- 伏笔是否超期、变义或提前消费，因果债和关系是否无过渡回退。

章节总结只核对状态增量，不替代仓库。正文与投影冲突时从 committed 正文证据重建投影，不用投影覆盖正文。输出只分“硬伤、风险、伏笔状态、通过项”，每个硬伤给出证据位置和修复方向。
