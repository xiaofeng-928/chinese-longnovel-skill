# 项目结构与迁移

本文是 vNext 项目文件结构、manifest、计划节点和事务提交的唯一权威；`项目定位.md` 只负责项目选择与初始化路由。

## manifest（novel-config.md）

`novel-config.md` 是项目 manifest，控制在 60-100 行以内，只保存：

- 不可变项目 ID、书名、项目状态、目标读者和一句话定位。
- 默认规模：1000 章以上。
- 当前权威文件路径表。
- 当前文风版本和生效章节、当前系统设定版本、当前计划窗口。
- 当前/下一窗口合同 ID 和剧情预算锁；详细剧情约束仍保存在总大纲窗口块中。
- 兼容模式和最近迁移日期。

manifest 使用稳定标题和 `键：值`，路径一律为项目根目录下的相对路径。最低 schema 见下。

```markdown
# 项目清单
- schema_version：3
- migration_state：legacy / staging / active
- legacy_scope：false
- legacy_source_hash：null
- legacy_snapshot_path：null
- operation_mode：normal / migration / maintenance / epub
- project_status：开书方案 / 系统设计 / 总纲 / 细纲 / 正文中 / 完结
- project_id：<UUID v4，创建后不可变>
- 书名：
- 产品类型：长篇经营类系统爽文
- 系统模式：required
- 经营主线：true
- 目标章数下限：1000
- 当前计划窗口：第1-50章
- 下一计划窗口：null
- 规划窗口协议版本：null
- 当前窗口合同：null
- 当前剧情预算锁：null
- 下一窗口合同：null
- 下一剧情预算锁：null
- 最近迁移日期：null
- 文风版本：v1.0
- 文风生效节点：chapter-0001
- 系统设定版本：v1.0
```

### 核心字段类型

- `schema_version`：整数，当前只接受 `3`；未知版本必须停止。
- `migration_state`：`legacy / staging / active`；`staging` 必须搭配 `operation_mode: migration`。
- `operation_mode`：`normal / migration / maintenance / epub`；普通正文事务看到非 normal 即停止。
- `project_status`：`开书方案 → 系统设计 → 总纲 → 细纲 → 正文中 → 完结`，同状态重入允许，逆向修改禁止。
- `project_id`：规范小写连字符形式的 UUID v4，创建后任何普通写作、恢复、rebase、导出和改书名都不得改变。
- `legacy_scope`：布尔；`true` 只允许迁移器写入，并同时要求非空 `legacy_source_hash` 与 `legacy_snapshot_path`。
- `产品类型`：`长篇经营类系统爽文 / legacy-long-form`。
- `系统模式`：`required / legacy-none`。
- `经营主线`：布尔。
- `目标章数下限`：正整数；vNext 新项目不得小于 1000。
- 当前/下一计划窗口：`第X-Y章` 或 `null`。
- `规划窗口协议版本`：未准备新窗口时为 `null`；启用防抢跑流程后为 `1`。
- 当前/下一窗口合同：`window-XXXX-YYYY` 或 `null`，范围必须与对应计划窗口一致。
- 当前/下一剧情预算锁：`locked` 或 `null`；有合同且准备生成细纲时必须为 `locked`。
- 文风/系统版本：`v<整数>.<整数>` 或 `null`。
- 生效节点：合法 `node_id` 或 `null`。
- 最近迁移日期：`YYYY-MM-DD` 或 `null`。
- 非空权威路径使用 `/` 分隔的项目根相对路径，解析后的绝对路径必须仍位于项目根目录。

### 生命周期必需文件

| `project_status` | 必须存在 | 可延迟 |
|---|---|---|
| `开书方案` | manifest、开书方案、参考素材 | 全部设定、计划、状态仓库 |
| `系统设计` | manifest、开书方案、参考素材、系统设定、文风 v0.9；仅 `系统模式: required` 使用 | 世界观、角色、计划、状态仓库 |
| `总纲` | manifest、开书方案、参考素材、世界观、角色、总大纲、文风 v1.0；required 时加系统设定 | 50 章计划、运行态仓库 |
| `细纲` | 总纲所需文件、当前剧情细纲、章节序列、genesis commit head；required 时加当前系统计划 | 状态仓库可在首章提交时创建 |
| `正文中` | 细纲所需文件、commit head、主角状态仓库；required 时加系统状态仓库 | 无 |
| `完结` | 与正文中相同，当前 head 所有节点 committed 且满足目标/提前完结条件 | 无 |

验证器按生命周期和能力标志检查，不因尚未进入某阶段而创建空文件。晋级必须先验证下一阶段必需文件，禁止先改 `project_status` 再补文件。

## 权威关系

| 状态层 | 唯一权威 | 不得存放 |
|---|---|---|
| 设计态 | `设定/系统设定.md`、`设定/世界观.md`、`设定/角色档案.md` | 当前余额、已完成任务 |
| 创作口径 | `创作依据/文风规范.md` | 范文原文例句、完整项目设定 |
| 宏观计划态 | `plan/总大纲.md` 的阶段块与窗口合同 | 当前真实状态 |
| 50 章计划态 | `plan/系统发展_第X-Y章.md`、`plan/大纲_第X-Y章.md` | 已发生事实快照 |
| 提交链 | `修复记录/生产状态/commit-head.json` + 可达的不可变 transactions | 未提交候选、共享文件整份历史哈希 |
| 工作副本 | `正文/` 当前可见文件 + `attempts/.../candidate.md` 快照 | current chain 已发生事实、`review_passed` 或 attestation |
| 当前运行态投影 | `总结/主角状态仓库.md`、`总结/系统状态仓库.md` | 未来计划、非当前 head 的增量 |
| 章节增量 | transaction 内不可变 summary/state delta；`总结/章节总结_第X-Y章.md` 是当前 head 投影 | 完整当前状态副本 |
| 长期记忆 | 阶段总结 | 全量角色/系统百科副本 |

已发生事实的裁决顺序：**从当前 commit head 沿 `parent_transaction_id` 可达且哈希匹配的正文**证据最高，不可变章节增量是该正文的结构化派生，状态仓库和 `plan/章节序列.md` 是当前 head 的可重建人类可读投影。`正文/` 中未被当前链引用的文件不具备事实权威。三者冲突时不得用投影覆盖正文，应从 committed 链重新生成受影响增量和投影。

`正文/` 允许作为用户持续修改的工作区，因此可见文件与 current chain 哈希不一致不等于 committed 事实被修改，也不自动触发 maintenance。审查当前文件时创建 `review_subject: working_copy` 的新 attempt，并同时保存 committed 基线哈希与当前工作副本哈希。工作副本审查证据不得进入 `review_evidence`、不得改变章节序列审查状态，也不得被 `validate_project.py` 当成 current chain 投影；只有用户明确要求把该版本正式纳入链时，才进入 committed 正文修订流程。

## 单写者锁

项目根 `.mynovel-write-lock.json` 使用原子 `CREATE_NEW` 获取，内容固定为 `lock_id`、`project_id`、`owner_id`、`operation`、`base_head_sha256`、`acquired_at`、`heartbeat_at` 和 `lease_until`。持锁者定期续租；未过期锁一律阻断。过期锁不能直接删除：恢复器先核对锁文件哈希、当前 head 和所有 prepared transaction，再用 compare-and-swap 改名为 `stale-lock-<lock_id>.json` 后重新获取恢复锁。

## 计划 schema

`plan/总大纲.md` 用连续阶段块覆盖第 1 章到 `目标章数下限`，不得有重叠或空洞：

```markdown
<!-- MYNOVEL:STAGE:stage-0001:START -->
- stage_id: stage-0001
- chapter_start: 1
- chapter_end: 250
- stage_status: planned
- exit_condition: 只有第201-250章窗口末才能完成的明确退出条件
<!-- MYNOVEL:STAGE:stage-0001:END -->
```

`stage_id` 全项目唯一；`stage_status` 只接受 `planned / active / completed / superseded`，锚点 ID 与字段必须一致。启用规划窗口协议后，当前被扩展阶段必须有非空 `exit_condition`。

总大纲的 50 章窗口合同使用：

```markdown
<!-- MYNOVEL:WINDOW:window-0051-0100:START -->
- window_id: window-0051-0100
- stage_id: stage-0002
- chapter_start: 51
- chapter_end: 100
- window_status: prepared
- stage_exit_allowed: false
- system_plan: plan/系统发展_第51-100章.md
- must_complete: 当前窗口必须结算的内容
- advance_only: 只能推进、不得完成的内容
- protagonist_progress_cap: 主角身份、能力、资源、关系和地图推进的窗口末计划上限
- system_progress_cap: 系统等级、权限、商品、任务和资源额度的窗口末计划上限
- forbidden_early_completion: 禁止提前完成的阶段任务和解锁
- reserved_for_later: 后续窗口专属剧情负载
- end_unresolved: 窗口末必须保留的矛盾或债务
- next_stage_forbidden: 禁止借用的下一宏观阶段内容
- next_window_id: window-0101-0150
- five_chapter_budget_status: locked

## 五章剧情预算
| 五章组 | 本组职责 | 允许结算 | 禁止越过 | 必须留给后组 |
|---|---|---|---|---|
| 第51-55章 | ... | ... | ... | ... |
<!-- MYNOVEL:WINDOW:window-0051-0100:END -->
```

- 窗口块不得嵌套在 `MYNOVEL:STAGE` 块内，统一放入总大纲“规划窗口合同”部分。
- 首次扩展某宏观阶段时，必须一次创建覆盖整个阶段的全部连续窗口；每个窗口不超过 50 章。
- 只有该宏观阶段最后一个窗口允许 `stage_exit_allowed: true`；非最后窗口必须保留非空 `reserved_for_later`、`forbidden_early_completion` 和 `end_unresolved`。
- 目标细纲窗口的 `five_chapter_budget_status` 必须为 `locked` 并存在五章预算表；未来保留窗口可为 `pending`。
- 完整流程、manifest 指针切换和旧项目兼容规则见 `references/规划窗口与防抢跑.md`。

50 章细纲中的每个节点使用：

```markdown
<!-- MYNOVEL:PLAN-NODE:chapter-0001:START -->
- node_id: chapter-0001
- planned_main_chapter: 1
- node_type: main
- mainline_anchor: stage-0001
- plan_status: planned
- task_refs: []
<!-- MYNOVEL:PLAN-NODE:chapter-0001:END -->
```

- `node_id` 全项目稳定且唯一，不因文件名或显示章号变化而改变。
- `node_type` 为 `main / insert / side`。每个当前窗口章号必须恰有一个 main 节点；insert/side 引用其 `planned_main_chapter`，不占用新的 main 章号。
- `plan_status` 为 `planned / consumed / superseded`。只有章节事务提交时才能把节点原子推进为 consumed。
- `task_refs` 使用 `[]` 或方括号内逗号分隔的稳定任务 ID；正文不得创建未被系统阶段计划引用的任务。

## commit head 与不可变事务

- genesis head：`project_id`（与 manifest 一致）、`head_transaction_id: tx-genesis`、`parent_transaction_id: null`、`generation_id: gen-0001`、`committed_node_id: null`。
- 每个事务目录通过 `CREATE_NEW` 一次性创建，重复 transaction ID 必须拒绝。`manifest.json` 记录 `project_id`、`transaction_id`、`parent_transaction_id`、`generation_id`、`base_head_sha256`、`node_id`、`attempt_id`、`sequence_event`、规范化 `manifest_sha256`、`review_status` 和 `review_evidence`。
- 项目文件作为输入时先校验项目相对路径和 SHA-256，再复制到该事务的不可变 `assets/` 快照；后续共享投影变化不得使旧事务资产失效。
- 创作事务必须包含 `state_validation_report_sha256`，并以 `review_status: review_pending` 提交；缺少状态回证不能 prepare。`naturalization_review_sha256` 与 `context_review_sha256` 是后置审查证据，只有标记 `review_passed` 时才必须同时存在并绑定当前正文哈希。
- 正文资产路径必须与审查状态一致：`review_pending` 事务中的可见正文路径以 `（草稿）.md` 结尾；`review_passed` 事务中的可见正文路径不得包含该后缀。普通创作提交、总结物化、状态更新和手动自然化都不能提前去掉“草稿”。
- transaction manifest 不可原地修改。后置审查通过且正文未变化时，追加一个绑定原正文资产、两份正式审查与状态回证的 `review_attestation` 事务，把当前正文哈希投影为 `review_passed`；该事务不重写语义总结或仓库。正文发生修改时改走修订/rebase 事务，不能用 attestation 掩盖正文变化。
- `commit-head.json` 是唯一 commit point，通过 head CAS（compare-and-swap）从 parent 指向新事务；任何 CAS 前提变化即废弃事务，不能覆盖另一合法提交。
- 崩溃恢复只处理不可变资产和 head：head 仍为 parent 时新事务是不可达孤儿；head 已指向新事务时以新链重新物化投影。
- head 保存规范化 `commit_hash`、从 genesis 到 current head 的 `chain_hash` 和当前投影哈希。`plan/章节序列.md` 的 `materialized_head_transaction_id` 与 `materialized_head_sha256` 必须绑定该 head；未提交正文和不可达事务会被项目验证器阻断。

## 兼容迁移

- `migration_state: legacy` 只读旧路径；`staging` 同时读取新旧文件做比对，禁止正文生产；`active` 只读写新路径。
- 旧项目无 `schema_version` 时只在内存中视为 `migration_state: legacy`，先快照再生成 v3 staging manifest，不能原地补字段冒充已迁移。
- 迁移完成前保留旧文件；新旧不一致时输出逐项冲突表并停止，不自动合并或选边。
- 用户确认切换后，把旧路径原样移动到项目内 `legacy/v2.0/` 并记录归档哈希；vNext 运行时永远不加载 `legacy/`。

## 维护性插入与 committed 正文修订

在当前 committed 尾部之后追加插入章可走普通单章事务。仅在用户明确要求把某个工作副本或其他改稿正式纳入 current chain 时，才视为“修改 committed 正文字节”；若目标位置之后已经存在 committed 节点，则必须进入显式 rebase。单纯编辑或审查 `正文/` 工作副本不自动启动 rebase：

1. 先读取 normal head 并创建项目快照与哈希清单，再获取项目写锁；不得先改 maintenance 后才拍快照。
2. 提交一个 `rebase_start` 控制事务，在同一次 head CAS 中保存 `rebase_id`、`base_head_transaction_id`、旧 `generation_id`、新 `generation_id` 和 `operation_mode: maintenance`。commit head 中的 operation mode 是运行时权威，manifest 只是其物化镜像；此后普通正文、迁移和 EPUB 都会被阻断。
3. 在 `修复记录/生产状态/rebases/<rebase_id>/` 保存不可变 rebase manifest。新代际从受影响节点前一个 committed transaction 分叉，后续每个重放 transaction 通过自己的 `parent_transaction_id` 串成平行链；旧 generation 继续作为当前只读链，rebase shadow 不进入正文上下文。
4. 按新物理顺序逐节点重新组装上下文，独立复审正文并重建 summary/state delta；若插入导致既有正文因果、认知或时间线失效，停止让用户决定改文还是放弃 rebase。从影响点顺序重放到旧 head，单次仍最多 5 章，跨会话通过 head 中的 `rebase_id` 保持 maintenance。
5. 全部后继节点验证通过后，重新获取短期写锁，并 CAS 确认当前 head 仍是同一 `rebase_start`。一次原子 head 替换同时切换到新 `generation_id + head_transaction_id + operation_mode: normal`。
6. 放弃或失败时提交 `rebase_abort` 控制事务，把 head 切回旧 generation 的同一内容头并恢复 `operation_mode: normal`；快照用于验证和灾难恢复，不会把项目留在 maintenance。旧代际与失败新代际均保留到用户另行授权清理。
