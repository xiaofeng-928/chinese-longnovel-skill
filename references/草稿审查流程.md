# 草稿审查流程

## 职责

负责草稿审查，只输出审查报告，不默认修改正文。

正式审查接收草稿生成后的 `（草稿）` 文件；正文已在生成阶段按去AI味写作风格写到位，不再有独立的润稿阶段。

## 范围限制

- 草稿审查一次最多 5 章。
- 超过 5 章必须要求拆分。

## 审查模式

用户明确说“完整审查/full”时请求 `full`；说“轻量审查/lean”时请求 `lean`；说“单线程审查/solo”时请求 `solo`；未指定时默认 `full`。

- `full`：检查硬事实、主线/细纲偏离、角色、时间线、信息流、节奏和禁用词。
- `lean`：检查硬事实、主线/细纲偏离、角色、时间线和信息流，不展开完整文风审查。
- `solo`：当前会话独立完成审查，不调用子 Agent。

报告必须写明：

```text
Requested Mode: full | lean | solo
Effective Mode: full | lean | solo
Fallback: none | missing agents -> solo | agent tool unavailable -> solo | spawn failed -> solo
```

当前 MyNovel 没有强制部署 reviewer Agent；无法调用子 Agent 时，`Effective Mode` 必须为 `solo`，不得声称完成了 full/lean 的并行审查。

## 审查输入

- 目标正文
- 本章大纲
- 最近 20 章章节总结
- 最近 3 章正文
- 当前阶段总结
- `novel-config.md`
- `总结/主角状态仓库.md`
- 角色档案、伏笔追踪表、写作铁律
- 采用文风系统的项目：`novel-config.md` 文风配置 + `文风/项目文风规范.md` + `文风/文风校准记录.md` 当前版本之后仍有效的校准项
- 可用脚本输出

## 逻辑依赖表

审查前必须派生审查逻辑依赖表，且必须包含关键时间锚。

审查逻辑依赖表至少包含：

- 本章前已经确立的硬事实
- 本章涉及的关键时间锚
- 角色在本章开始前知道什么、不知道什么
- 主角和关键角色当前能力/资源
- 主角状态仓库中的当前真实状态，以及本章正文/章节总结造成的状态增量
- 关系状态
- 信息流边界
- 因果债与未解决冲突
- 后文禁止误写

## 问题分类

- A 类：硬伤，必须修。包括时间线矛盾、角色认知越界、硬事实冲突、能力越级、信息流泄露、伏笔含义变形。
- B 类：风险或体验问题。包括节奏拖沓、爽点弱、表达重复、情绪铺垫不足。

## 脚本证据

- 如果 `scripts/count_chars.py` 存在且适用，优先运行脚本。
- 审查报告引用 `count_chars.py` 输出作为字数等量化证据。
- 采用文风系统且配置来源范文的项目，运行 `scripts/原文重合检查.py` 检查连续文本重合；审查报告记录结论和必要位置，临时重合检查报告不进入长期上下文。
- 如果脚本不存在，报告中注明未使用脚本，不临时创建替代脚本。

## 项目文风一致性检查

采用文风系统的项目，草稿审查新增独立的“项目文风一致性”检查，不与通用 AI 味检查混为一项。审查只报告具有正文证据和修改价值的偏移：

- 硬规则违反；
- 叙事视角或距离漂移；
- 同类场景连续偏离项目场景模式；
- 角色规格卡被全书文风覆盖；
- 通用模型模板重新出现；
- 与来源范文存在连续文本重合风险。

单个句子没有命中软倾向，不构成问题。不得为了追求统计完全一致，把正文机械修成平均值。审查报告增加：

```markdown
## 文风执行核对
- 项目文风版本：
- 场景模式匹配：通过 / 偏移
- 硬规则：通过 / 违反
- 软倾向整体一致性：稳定 / 轻微漂移 / 明显漂移
- 角色声音优先级：通过 / 被项目文风覆盖
- 原文重合检查：通过 / 需复核 / 阻断
- 证据位置：
```

未采用文风系统的项目不输出该核对块。

## 审查报告

- 审查报告写入对应 50 章归档文件。
- 报告必须明确章节、问题位置、问题类型、前文依据和修复建议。
- A 类问题必须给出“为什么影响后文逻辑”的说明。
- 默认审查后停止，不自动修复。

## 审查后动作

- 默认停止，不自动修复。
- 用户明确说“修复”“审查并修复”时，进入 `草稿修复流程.md`。
