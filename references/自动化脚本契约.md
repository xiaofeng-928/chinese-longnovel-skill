# 自动化脚本契约

## 职责

规定未来 MyNovel Skill 内置脚本的文件名、用途、调用方式和输出用途。

## 脚本目录

通用脚本放在：

```text
<Skill根目录>/scripts/
```

单本小说专属导出脚本仍放在小说项目目录，例如 `convert_to_epub.py`。

## 已实现脚本

- `count_chars.py`：唯一字数统计入口（省略号加权口径），支持文件和目录。
- `文风统计.py`：范文正文确定性文体统计（总字符/章节/句子/段落数、句长与段长分位数、对话占比、标点频率、词类频率、同构句与重复短语候选、按章节统计）。
- `原文重合检查.py`：草稿与来源范文的连续字符重合检查，支持多来源和白名单，输出含标点与去标点两种口径，阈值集中定义。
- `项目事务.py`：manifest、单写者锁、genesis/commit-head 链、不可变事务资产快照、审查状态/状态回证哈希、head CAS 和维护代际控制。模块，非独立 CLI。
- `validate_project.py`：检查 manifest、生命周期、STAGE/WINDOW/PLAN-NODE schema、剧情预算锁及其非占位内容、commit 链、投影、未提交污染、维护状态与 EPUB 构建清单。
- `validate_chapter_candidate.py`：分阶段独立校验生成/自然化候选、工作副本、正式 repair、双独立审查和状态回证；普通生成使用 `naturalization_result: not_requested` 且源稿/候选必须字节一致。事实锁的非空 `expected_value` 必须闭合来源与候选锚点，数值比较覆盖前后置数值及升、吨、秒、伏、瓦等小说常用单位。每个 pass 维度必须提供非空证据。`--allow-working-copy` 固定不可提交；`--allow-repair` 要求 repair-basis、approved-changes、双审和状态回证全部闭合，只有批准差异可以越过 committed 基线。
- `formalize_reviewed_drafts.py`：在两路独立审查已经真实完成后，把作者批准的当前可见修复稿按真实差异块创建 repair attempts，并自动执行可回滚的 shadow rebase；支持已带正式文件名的再次修订，只为正文哈希实际变化的章节创建修复事务。`--apply` 必须同时提供 `--independent-reviews-confirmed`，该参数只能由已取得两路独立复审结果的编排者使用。
- `migrate_plan_nodes.py`：旧 50 章细纲的一次性 PLAN-NODE 机械迁移；已存在标记时拒绝覆盖。
- `refresh_genesis_projection.py`：仅用于正文为空的 genesis 迁移项目，刷新计划投影和章节序列绑定；检测到正文时拒绝执行。

## 调用原则

- 脚本是普通本地命令行工具，不依赖隐藏 hook。
- Claude Code、Codex 和子 agent 都通过 shell 调用脚本。
- 脚本存在且适用时，优先使用脚本输出作为证据。
- 脚本不存在时，不临时创建替代脚本；在报告中注明未使用脚本。
- 脚本输出可写入审查报告、验证结论和修复记录。
- 脚本负责输出事实和证据，不负责判断模糊用户意图。模糊定位、取舍和追问仍由 Agent 完成。
- 默认输出 JSON；需要可读报告时可加 `--format markdown`。

## 命令契约

使用当前平台可用的 Python 3 启动命令：Windows 优先尝试 `py -3`，macOS/Linux 优先尝试 `python3`，其他环境可使用明确指向 Python 3 的 `python`。不得因某一个命令名不可用就误判为缺少 Python 环境。下方以 `<python3>` 和 `<Skill根目录>` 表示解析后的实际命令与安装目录，报告中记录实际使用的命令。

### count_chars.py

用途：唯一字数统计入口（省略号加权口径）。支持文件和目录。

```powershell
<python3> "<Skill根目录>/scripts/count_chars.py" "<项目根>/正文/第001章_绝境.md"
<python3> "<Skill根目录>/scripts/count_chars.py" "<项目根>/正文/"
```

字数统计口径（审查口径）：非空白字符 + 省略号加权（`……` 算 6、`…` 算 3）。由 `公共工具.count_review_chars` 实现。

### 文风统计.py

用途：对范文正文做确定性文体统计，只输出可计算事实，不输出文学判断。文风蒸馏时按 `范文与创作依据.md` 的样本计划分层取样后调用。

```powershell
<python3> "<Skill根目录>/scripts/文风统计.py" profile --text <正文.txt> --index <章节索引.md> --chapters <章节选择表达式> --output <文风统计报告.md>
<python3> "<Skill根目录>/scripts/文风统计.py" profile --text <正文.txt> --index <章节索引.md> --chapters 1-3,8-10
```

关键输出：`total`（chars/chapters/sentences/paragraphs/对话占比）、`sentence_lengths` 与 `paragraph_lengths`（mean/p25/median/p75/p90）、`punctuation`（逗号/句号/问号/感叹号/省略号/破折号频率）、`word_classes`（连接词/反应词/程度副词/转场词频率）、`candidates`（同构句与重复短语候选）、`chapters`（按章节分别统计）。

### 原文重合检查.py

用途：检查草稿与来源范文之间的连续字符重合，支持多来源。只检测规范化后的连续字符重合，不判定语义近似抄袭。阈值集中定义并配有单元测试。

```powershell
<python3> "<Skill根目录>/scripts/原文重合检查.py" check --draft <草稿文件> --source <范文正文.txt> --output <临时检查报告.md>
<python3> "<Skill根目录>/scripts/原文重合检查.py" check --draft <草稿文件> --source <范文A正文.txt> --source <范文B正文.txt> --whitelist <白名单文件>
```

阈值：连续重合 16-23 个中文字符为 `需复核`；24 个及以上为 `阻断`；12-15 个中文字符只有在同一表达重复命中两次以上时才报告。专名、系统固定提示和类型公共术语可通过白名单豁免，但必须在输出 `exempted` 中记录。多来源用重复 `--source` 传入。临时重合检查报告默认不进入小说长期上下文；审查报告只记录结论和必要位置。

### validate_project.py

用途：项目结构验证器。在项目定位、迁移、一致性检查、正文生产前运行，提供确定性结构事实。

```powershell
<python3> "<Skill根目录>/scripts/validate_project.py" --project-root <项目根>
<python3> "<Skill根目录>/scripts/validate_project.py" --project-root <项目根> --json
```

关键输出（JSON）：`ok`、`checks.manifest`、`authority`、`plan`、`anchor`、`stage`、`window_contract`、`plan_schema`、`chain`、`projection`、`runtime`、`epub` 与 `duplicate_authority`。退出码 `0=通过`、`1=未通过`。

- manifest 是否缺少必填键、schema 是否合法、`project_id` 是否为 UUID v4、权威路径是否越出项目根。
- 正文文件名是否与事务审查状态一致：`review_pending` 必须带 `（草稿）`，`review_passed` 必须去掉该后缀。
- 当前生命周期与系统模式声明的权威文件是否真实存在（文档 3.7 的断链回归）。
- plan 文件是否携带“已发布章节/当前写到”等过期运行态（文档 3.8）。
- HTML 锚点是否重复或未配对（文档 9.4）。
- STAGE 是否连续覆盖目标，PLAN-NODE 是否唯一、完整且 task refs 合法。
- 启用 `规划窗口协议版本：1` 后，WINDOW 是否完整覆盖被扩展宏观阶段、阶段退出权限是否只属于最后窗口、后续剧情保留量是否非空、锁定窗口的每个五章组是否连续覆盖全部章号且四个预算单元均为非空非占位内容，以及 config 当前/下一合同、预算锁和系统计划路径是否一致；未启用协议的旧项目保持兼容。
- commit head 是否能沿 `parent_transaction_id` 无环回到 genesis，project ID、manifest、资产快照和审查证据是否闭合。
- 章节序列与 head 是否绑定，是否存在孤儿 transaction 或未提交正文污染。
- maintenance/rebase 状态及 EPUB export manifest 的项目、source head、build 和哈希是否闭合。
- 文风、系统、角色、世界观是否出现重复权威块。

### validate_chapter_candidate.py

严格提交候选：

```powershell
<python3> "<Skill根目录>/scripts/validate_chapter_candidate.py" --attempt-dir <attempt> --project-root <项目根>
<python3> "<Skill根目录>/scripts/validate_chapter_candidate.py" --attempt-dir <attempt> --project-root <项目根> --require-reviews
```

当前可见稿与 committed 正文哈希不一致时使用工作副本模式：

```powershell
<python3> "<Skill根目录>/scripts/validate_chapter_candidate.py" --attempt-dir <attempt> --project-root <项目根> --allow-working-copy --require-reviews
```

用户明确要求修复后使用正式 repair 模式：

```powershell
<python3> "<Skill根目录>/scripts/validate_chapter_candidate.py" --attempt-dir <attempt> --project-root <项目根> --allow-repair --require-reviews --require-state-validation
```

- `naturalization.md` 必填 `review_subject: working_copy`、`base_committed_sha256`、`working_copy_sha256`、`working_copy_path`；`candidate.md` 必须与该路径当前文件字节一致。
- 每条事实锁仍以 `workspace/source.md` 的 committed 基线为来源，并额外提供 `working_copy_anchor` 与 `working_copy_anchor_sha256`；非空 `expected_value` 必须同时存在于两个锚点。旧 `source_path` 已漂移时只告警；不可变基线、当前锚点、受保护数值、任一审查维度的证据为空或双审查任一失败仍返回退出码 1。
- 工作副本模式不能与 `--require-state-validation` 同用，不能使用 `review_passed` 状态，也不能作为提交准备、正文改名或 review attestation 的输入。
- repair attempt 必填 `review_subject: repair`、committed/候选/repair-basis/approved-changes 四份哈希和 `repair_target_path`；事实锁使用 `repair_anchor`。`approved-changes.json` 必须用唯一且不重叠的源/候选锚点精确覆盖全部正文差异；每对锚点只能执行一次其声明的 `old_value` → `new_value` 替换，不能用整段锚点夹带其他改写。清单还必须闭合全部受保护数值和极性差异，并把每项变化绑定 repair-basis 问题证据。声明 `summary_rebuild`、`state_rebuild` 或 `rebase` 时，状态回证分别强制非空 `deltas/summary.md`、非空 `deltas/state.json` 及其哈希。通过后 `eligible_for_review_passed: true`，进入修订事务或 shadow rebase。

### 项目事务.py

用途：vNext 项目 schema 与原子提交的共享模块，不独立运行。提供 `parse_manifest`、`validate_manifest`、`WriteLock`、`create_genesis`、`read_head`、`prepare_transaction`、`chain_parents`、`verify_chain`、`commit_head_cas`、`rebase_start`、`rebase_abort`、`rebase_complete`、`plan_activation`。正文生产、状态总结和 EPUB 导出都通过它获得当前 head 与写锁，禁止绕过该模块直接改 `commit-head.json`。

- `prepare_transaction` 的 `review_pending` 创作事务只要求 `state_validation_report_sha256`；`review_passed` 事务才要求 naturalization/context 两份审查哈希。两份正式审查证据必须成对出现，并由不可变事务资产支持。

- `rebase_start` / `rebase_abort` / `rebase_complete`：晚插章和 committed 正文修订的 maintenance rebase 控制事务。`rebase_start` 先持久化不可变 rebase manifest，再以 head CAS 把 operation mode 置为 `maintenance` 并保存新旧代际；写 manifest 失败不得改变 head。`rebase_abort` 把 head 切回旧 generation 并恢复 `normal`；`rebase_complete` 校验目标 shadow 链确实后接本次 base transaction、目标事务属于新代际，再以 CAS 原子切换最终 head、投影哈希并恢复 `normal`。maintenance 期间普通正文、迁移和 EPUB 都会被阻断。
- `plan_activation`：50 章双窗口协议。当前窗口最后一个 main 节点 committed 后，切换当前/下一窗口路径并清空三个下一字段。

### formalize_reviewed_drafts.py

用途：把已获两路独立复审通过的连续修复范围正式写回。脚本比较 current chain 与当前可见正文，只为实际变化章节创建精确 `approved-changes.json`、repair attempt 和修订事务；若范围后已有 committed 节点，则自动创建快照、进入 maintenance、重放后文并原子切换新代际。已经没有“（草稿）”后缀的正式正文可再次修订，脚本不得自拷贝或删除同路径文件。

```powershell
<python3> "<Skill根目录>/scripts/formalize_reviewed_drafts.py" --project-root <项目根> --start 1 --end 50
<python3> "<Skill根目录>/scripts/formalize_reviewed_drafts.py" --project-root <项目根> --start 1 --end 50 --apply --independent-reviews-confirmed
```

- 不带 `--apply` 只报告与 current chain 哈希不同的章节。
- `--independent-reviews-confirmed` 是显式编排门禁，不替代独立模型调用本身；没有两路真实复审结果时不得提供该参数。
- 批准清单按差异块生成，插入或删除使用相邻不变行形成双锚点，不允许整章宽锚点夹带修改。
- 失败发生在 maintenance 前时清理本轮未完成 attempt 与空快照；进入 maintenance 后失败则调用 `rebase_abort` 恢复旧代际与 normal 模式。

## 审查证据写入规则

### 扫榜.py

“扫榜.py”是数据规范化和聚合器，不是抓榜器。它只处理已取得的结构化榜单记录，做 schema 校验、URL 规范化、平台内去重、跨平台疑似重复分组和市场验证计数；网络抓取、登录态和平台反爬由外部工具或用户提供的数据负责，脚本不伪造当前热度，也不替用户自动拍板。

输入：UTF-8 JSON（根对象固定为 `{"schema_version": 1, "records": [...]}`）或 CSV（第一行为字段名）。必填字段：`source_platform`、`list_name`、`snapshot_date`、`title`、`url`、`captured_at`；`url` 缺失即 schema 无效。`genre_tags` 与 `evidence_dimensions` 只接受合法枚举。

输出（JSON）：`status`、`valid_count`、`market_validation_count`、`fresh_market_validation_count`、`latest_snapshot_date`、`deduplicated_count`、`possible_cross_platform_duplicates`、`conflicts`、`archive_path`、`sha256`、`reused`。人类可读说明写到标准错误，禁止破坏 JSON 标准输出。

退出码：`0=ready`、`2=schema_invalid`、`3=insufficient_samples`、`4=stale_evidence`、`5=dedup_conflict`、`6=archive_io_error`。`market_validation_count < 5` 返回 `3`；新鲜匹配少于 5 返回 `4`；只有 `fresh_market_validation_count >= 5` 才能 ready。多种错误同时存在时按 `2→5→6→3→4` 优先级返回。

归档：规范化后唯一写入 `<长篇范文库>/扫榜/YYYY-MM-DD_经营系统_<来源范围>_<完整内容SHA256>.json`。调用时显式传入 `--archive-dir <长篇范文库>/扫榜`；未传入时，脚本按 `MYNOVEL_WORKSPACE` 或当前工作目录解析，存在 `小说/` 层时使用其下 `范文/`，否则直接使用工作区下 `范文/`。归档不可变，同路径文件的实际 SHA-256 必须等于文件名绑定的内容哈希才能返回 `ready` 与 `reused: true`；不一致返回 `archive_io_error`，不提供 `--force` 改写。项目内只在 `创作依据/开书方案.md` 记录归档相对标识、完整 SHA-256 和选用记录，不复制整份榜单。

- 匹配作品必须包含 `management_loop` 或 `system_loop` 证据才计入市场验证下限；唯一作品键依次使用跨平台 `canonical_work_id`、平台内 `work_id`、规范化 URL，同一作品的多个 URL 不得重复计数。纯文风样本可进入参考素材，但不计入 5 本下限。
- 审查报告中引用脚本结果时，写明脚本名、命令目的和关键 JSON 字段。
- `count_chars.py` 的输出是字数统计的优先证据。
