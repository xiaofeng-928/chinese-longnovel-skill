# MyNovel — Claude Code 网络小说写作 Skill

当前版本：**v1.5.0**

> 用 AI 写网络小说，但不写成流水账。

MyNovel 是一个 Claude Code Skill，把网络小说的完整创作流程——从大纲到完稿——封装成一套结构化工作流。它不是"帮我写一章"的简单 prompt，而是一个有记忆、有审查、有纠错的写作系统。

## 它能做什么

| **扫榜与选题** | 汇总平台榜单证据，分析题材热度、竞争风险和用户匹配度，生成“选题决策.md” |
| **范文拆书与原创仿写** | 将确认的榜单样本按平台和大类题材入库，基于合法全文拆解，并生成通过原创性闸门的项目迁移方案 |

| 阶段 | 说明 |
|---|---|
| **大纲生成** | 从题材/设定出发，输出包含阶段划分、角色档案、伏笔追踪表的完整大纲 |
| **分阶段大纲细化** | 将总大纲按阶段拆解为逐章细纲，50 章一归档 |
| **黄金三章微操** | 生成第1-50章常规细纲前，先为前三章做情绪节拍/台词/红线级别的微操细纲 |
| **正文生成** | 逐章写作，按有效章节序列组装最近节点、主线锚点、章节总结、阶段记忆和设定上下文（旧提示词文件名保留“草稿”以兼容项目） |
| **草稿审查** | 四类问题检测：A 类硬伤（零容忍）、B1 人物偏移、B2 节奏、B3 AI 味（量化阈值） |
| **细纲整理** | 将流水账、手写构想或笼统细纲整理成可直接指导正文的正式细纲 |
| **自动修复** | 审查后自动修复必改项，修复后局部复查，不全章重审 |
| **章节总结** | 每章写完自动生成总结，为后续章节提供上下文 |
| **一致性检查** | 跨章节检查角色状态、伏笔回收、时间线等一致性问题 |

## 为什么需要这个

直接让 AI 写网络小说会遇到三个问题：

1. **写着写着就偏了** — 角色性格漂移、伏笔遗忘、时间线矛盾。原因是没有结构化的记忆层。
2. **AI 味太重** — 万能副词泛滥、"告诉代替展示"、反应词堆砌。原因是没有量化检测。
3. **长篇写不动** — 超过 20 章上下文就爆炸。原因是没有上下文压缩机制。

MyNovel 的设计就是为了解决这三个问题：

- **三层上下文金字塔**：近邻章节总结（20-30 章）防细节写偏，阶段总结防走向走偏，历史阶段总结防硬伤。
- **量化审查**：AI 味不是主观判断——反应词密度有阈值，"告诉代替展示"有扫描词表。
- **批次写作 + 上下文压缩**：正文创作、审查、自动修复当前会话每批最多 5 章；大纲、总结、审查报告仍按 50 章归档，控制上下文规模。

## 安装

### 前置条件

- [Claude Code](https://docs.anthropic.com/en/docs/claude-code) 已安装并可运行

### 安装步骤

```bash
# 克隆到 Claude Code skills 目录
git clone https://github.com/<your-username>/MyNovel.git ~/.claude/skills/MyNovel
```

安装后重启 Claude Code，Skill 会自动加载。

## 使用方式

在 Claude Code 中用自然语言触发，例如：

```
> 新小说，我想写一本都市修仙
> 大纲
> 细化第1-50章大纲
> 写第1章
> 审查第1-3章
> 审查并修复第1章
> 一致性检查
> 今天小说就到这
```

Skill 会自动路由到对应工作流，读取必要的参考文档和提示词，然后执行。

## 工作流概览

```
新小说初始化
    ↓
大纲生成 → 黄金三章微操细纲（第1-50章前置）
    ↓
分阶段大纲细化（按 50 章归档段）
    ↓
┌─ 正文生成 ─→ 章节总结 ─┐
│                          │  ← 批次循环（每批最多 5 章）
└──────────────────────────┘
    ↓
正文审查 → 自动修复 → 局部复查
    ↓
一致性检查（按需）
    ↓
会话结束：补齐总结 + 更新阶段总结
```

扫榜样本需要作为范文时，先走独立前置链路：

```text
扫榜 → 用户确认范文候选 → 按平台/大类题材入库 → 合法全文拆书
    → 项目级范文迁移方案 → 原创性闸门 → 新小说初始化/大纲生成
```

## 设计决策

### 上下文组装规则

上下文不再按章节数字机械回退：读取当前节点之前最近 3 个有效节点，并补读最近 1 个主线锚点；已写出但未审查的正文仍然参与上下文。详见 `references/章节序列.md`。

旧版六层上下文表仅用于解释历史设计，不覆盖上述现行规则。

| 层 | 内容 | 作用 |
|---|---|---|
| 1 | 当前章大纲 | 本章该写什么 |
| 2 | 上一章末尾 500 字 | 衔接语气和场景 |
| 3 | 近邻 20-30 章总结 | 伏笔回收、细节一致性 |
| 4 | 主角状态仓库 | 当前真实身份、能力、资源、关系、认知和剧情债务 |
| 5 | 当前阶段总结 | 阶段结算、关键时间锚、仓库核对 |
| 6 | 已完成阶段总结 | 防硬伤（死人复活等） |
| 7 | 小说设定/铁律 | 全局约束 |

主角状态采用“计划、增量、快照”三层分工：总大纲维护计划状态，章节总结维护正文造成的状态增量，`总结/主角状态仓库.md` 维护当前真实状态。后续正文、审查、修复和续写先读仓库，再用章节总结核对变化。

### 审查为什么只抓四类问题

草稿不是精品，要求完美会导致审查报告全是废话。但以下四类不修读者真会弃书：

- **A 类（硬伤）**：逻辑矛盾、设定冲突、时间线错误 — 零容忍
- **B1（人物偏移）**：性格规格卡对照检测
- **B2（节奏）**：拖沓/过快，与大纲节拍对比
- **B3（AI 味）**：量化检测；Tier 1 单个词达到 2 次、Tier 2 总数超过 3 次、Tier 3 总数超过 5 次时标红

### 为什么用性格规格卡而不是"性格关键词"

"扮猪吃虎、绝不降智"这种关键词，AI 写对话时不知道角色该用什么语气。性格规格卡包含：说话方式（语速/口头禅/情绪表达）、行为模式（4 种场景的默认反应）、禁写清单。每个有对话的角色都必须填写。

## 自定义

- **每本小说的配置**：在小说项目目录下创建 `novel-config.md`，定义阶段划分、角色体系、写作铁律等
- **修改审查规则**：编辑 `prompts/草稿审查提示词.md` 和 `prompts/草稿自动修复提示词.md`
- **调整上下文范围**：修改 `references/上下文组装.md` 中的近邻章节数
