# MyNovel v1.3 开篇与章末钩子设计稿

## 目标

v1.3 做两件事：

1. 把“开篇设计”和“章末钩子设计”融入现有的细纲、黄金三章微操细纲、草稿生成、草稿审查、草稿修复提示词。
2. 新增一个共享提示词，专门处理“怎么改”“给几个修改方案”“高风险修复先让用户选”的逻辑。

本版本不新增独立的“单章开头技法库”或“章末钩子库”。开篇和钩子的规则直接写进现有提示词里，保持 MyNovel 现在的工作流结构。

## 不做什么

- 不新增 `references/技法库/单章开头技法.md`。
- 不新增 `references/技法库/章末钩子库.md`。
- 不做“有效扩写与防注水”。
- 不做“对话潜台词与节奏”。
- 不扩展脚本功能，只保证现有脚本测试继续通过。
- 不推翻现有 MyNovel 流程，只在现有提示词里加首尾设计规则。

## 新增共享提示词

新增文件：

```text
prompts/修改建议与技法应用提示词.md
```

这个提示词不是新的正文生成流程，也不是新的审查流程。它只负责“修改建议怎么给”。

使用场景：

- 用户问：“你推荐怎么改？”
- 用户问：“给我几个修改方案。”
- 用户问：“这个问题怎么修？”
- 自动修复遇到高风险改动，需要先给用户 2-3 个方案选择。

它需要规定：

- 如何把审查问题转换成 2-3 个具体修改方案。
- 如何标注每个方案的改动范围、收益和风险。
- 哪些问题可以直接小修，哪些问题必须先让用户选择。
- 不得为了修得好看而新增主线事件、角色、设定、能力、伏笔。
- 不得提前消耗后续两章的核心事件。
- 推荐开篇或章末改法时，必须服从本章细纲和已拼接上下文。

## 现有提示词怎么改

### 1. `prompts/分阶段大纲细化提示词.md`

这里是 v1.3 的核心改动之一。

当前细纲里已经有：

```text
**爽点/钩子**：
- 爽点：
- 章末钩子：
```

v1.3 要在每章大纲格式中新增“开篇设计”：

```text
**开篇设计**：
- 开篇方式：（从可选开篇方式中选择一种）
- 承接上一章：（说明如何接住上一章结尾钩子/状态）
- 前20%牵引：（异常、压力、冲突、信息差或行动目标）
```

同时保留 `爽点/钩子`，但强化章末钩子字段：

```text
**爽点/钩子**：
- 爽点：（如有）
- 章末钩子类型：（从扩展后的可选类型中选择一种）
- 章末钩子：（结尾留什么期待驱动下一章）
```

现在提示词里只有四种钩子：

```text
悬念 / 逆转 / 升级预告 / 冲突预告
```

v1.3 直接在这个提示词里扩展，不另建钩子库。可选类型可以包括：

- 突然揭示
- 紧急危机
- 未完成动作
- 身份/立场反转
- 两难选择
- 神秘线索
- 时间限制
- 承诺/威胁
- 言外之意
- 回声/呼应
- 留白钩子
- 升级预告
- 冲突预告

还要保留现有“短期去重”思想：最近章节不能反复使用同一种章末钩子形态，除非是有意识的升级变体。

### 2. `prompts/草稿生成提示词.md`

草稿生成不重新设计大纲，但必须执行细纲中的开篇和钩子要求。

“先提取本章大纲硬要求”要扩展为提取：

- 开篇方式
- 承接上一章
- 前20%牵引
- 章末钩子类型
- 章末钩子
- 与下一章衔接

正文生成时要做到：

- 按本章细纲的开篇设计开场。
- 前 20% 必须形成进入感，可以来自行动、压力、异常、信息差、冲突或情绪牵引。
- 结尾必须按细纲指定的章末钩子类型和章末钩子收束。
- 不得为了让开头或结尾更强，提前写入后续两章的核心事件。

### 3. `prompts/黄金三章微操细纲提示词.md`

黄金三章微操细纲会直接生成第 1-3 章的微操级写作指引，并且发生在常规第 1-50 章细纲之前，所以需要和 v1.3 字段对齐。

不需要把它改成常规分阶段细纲格式，只做小改：

在每章输出格式中新增：

```text
### 开篇设计
- 开篇方式：
- 承接上一章：
- 前20%牵引：
```

第 1 章的 `承接上一章` 可以写：

```text
无，负责建立开篇承诺。
```

把原有 `### 章末悬念（钩子）` 强化为：

```text
### 章末悬念（钩子）
- 钩子类型：
- 最后一幕画面：
- 悬念点：
```

保留现有“章末钩子必须画面级”的要求。

### 4. `prompts/草稿审查提示词.md`

草稿审查要增加“开篇”和“章末钩子质量”检查。

新增检查项：

- 开篇承接：是否自然接住上一章结尾状态或钩子。
- 开篇牵引：前 20% 是否有行动、压力、异常、信息差、冲突或情绪牵引。
- 开篇偏离：是否无视细纲中的开篇设计。
- 章末钩子有效性：结尾是否给出具体的下一章期待。
- 钩子重复：近期章节是否反复使用同一种钩子形态，且没有升级。

如果用户只是审查，就在审查报告里列问题。

如果用户问“怎么改”“推荐怎么改”“给几个方案”，审查流程要读取：

```text
prompts/修改建议与技法应用提示词.md
```

然后输出可选方案，而不是只给一个唯一修法。

### 5. `prompts/草稿自动修复提示词.md`

自动修复要加入 v1.3 的“低风险直接修，高风险先给方案”规则。

低风险修复可以直接做：

- 把平淡结尾改成更有牵引力的一句话，但不改变事件。
- 调整第一段，让它更自然承接上一章，但不改变事件。
- 强化已有钩子句，但不改变钩子类型。

高风险修复必须先给用户 2-3 个方案：

- 改变本章开篇方式。
- 重排开头场景。
- 新增细纲里没有的开篇动作或信息。
- 改变章末钩子类型。
- 新增较大篇幅的结尾段落。
- 任何会影响节奏、事件顺序、角色认知、伏笔含义或后续两章边界的修复。

遇到高风险修复时，必须读取：

```text
prompts/修改建议与技法应用提示词.md
```

然后先输出方案，等待用户选择。除非用户明确说“你选最稳的方案直接改”，否则不能擅自大改。

### 6. `SKILL.md`

入口路由要更新：

- 在提示词列表中加入 `修改建议与技法应用提示词.md`。
- 增加“推荐怎么改 / 给几个修改方案 / 这个问题怎么修”这类意图的路由。
- 草稿审查和草稿修复流程只有在用户要求修改建议，或遇到高风险修复时，才读取这个共享提示词。

## 修改方案输出格式

共享提示词建议使用这种短格式：

```text
方案A：保守局部修
适用：
改动范围：
效果：
风险：

方案B：结构强化修
适用：
改动范围：
效果：
风险：

推荐：
```

如果确实有第三种方案，再给方案 C。方案必须具体，用户看完就能选，不要写成很长的理论分析。

## 成功标准

v1.3 完成后，一章的开篇和结尾应该形成闭环：

1. 细纲阶段设计开篇方式和章末钩子。
2. 草稿生成阶段按这些字段写正文。
3. 草稿审查阶段检查这些字段有没有落地。
4. 草稿修复阶段小问题直接修，大问题先给用户 2-3 个方案选择。
